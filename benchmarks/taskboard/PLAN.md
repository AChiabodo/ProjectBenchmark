# Plan — Taskboard: a multi-node board on Docker Compose

## 1. Goal and scope

Taskboard is the only benchmark in the suite where more than one process must be designed together: a
relational database, an HTTP API and a browser frontend that come up as one stack, agree on a network
contract, and keep a data invariant that a single-process application never faces. There is no
algorithmic novelty here on purpose: the difficulty is coordination — startup ordering, schema
evolution, an ordering invariant under concurrent moves, and a frontend that is more than the happy
path.

Everything runs offline. There is no external API, no remote asset, no downloaded font and no
telemetry; the only network in play is the Compose network between the three services.

### Final functionality

- three services — PostgreSQL, the API, the web frontend — started by one command, where the start
  command returns only when every service is healthy;
- a REST API over boards, columns and tasks: create, read, update, delete, reorder a column, and a
  move that carries a target column plus a target position;
- SQL migrations applied by the API at startup on an empty database, versioned and recorded, with the
  applied version visible from the health endpoint;
- a Svelte frontend with TypeScript, built to static files, that consumes that API through the same
  origin and renders the board with declared empty, loading and error states;
- a deterministic seed command that reproduces the same ids, the same column order and the same task
  order on every fresh volume;
- API tests that run inside the container against the containerised database, never against a mocked
  one;
- one headless browser path across the real stack, asserting observable state and nothing visual;
- `./verify.sh` writing `verify.json` with every milestone id.

### Non-goals

Authentication, roles, invitations, multi-tenancy. Realtime collaboration, websockets,
notifications. Drag-and-drop polish and animation work: moves are explicit, labelled controls.
Pagination, search, filters, labels, attachments, comments, activity history. Deployment, hosting,
publishing, CI, release automation. Native or mobile clients. Server-side rendering: the frontend
is a static build, and the only HTML the browser receives comes from files.

## 2. Locked technical decisions

### Topology

```text
browser ──HTTP──> web   nginx 1.27.2, static Svelte build, /api proxied
                    │
                    └──────> api   Node.js 22, Fastify 5.2.1, TypeScript 5.8.3
                                     │
                                     └──> db   PostgreSQL 16.4
```

- Two images are built from this repository (`api`, `web`); the database is a pinned public image.
- The web image is `nginx` serving `dist/`; it holds no application logic and no server-side
  rendering. The API is the only process that opens a database connection, and the browser never
  reaches PostgreSQL.
- Everything the browser calls is same-origin: nginx proxies `/api/` to the API and publishes it
  under the same host and port as the static files. Consequence, and a deliberate constraint: no CORS
  configuration exists anywhere, and no `Access-Control-*` header is part of the contract.
- The API also serves `/healthz` at its own root, on the Compose network only; `npm run health` in
  the `api` container prints it, which is how the schema version is read without publishing a
  database or an API port to the host.

### Stack

```text
api:  Node.js 22.13.1, ESM, strict TypeScript compiled with tsc, Fastify 5.2.1, pg 8.13.1
db:   PostgreSQL 16.4, one database `taskboard`, one named volume
web:  Svelte 5 + TypeScript 5.8.3 + Vite 7.0.6, static build, nginx 1.27.2
test: Vitest 4.0.0 (API and frontend units), Playwright 1.65.0 with Chromium (one e2e spec)

```

### Commands — exactly one of each

```bash
docker compose up --wait --build      # the single start command
./verify.sh                           # the single verification command
```

`docker compose up --wait` is that same start command; `--build` only forces the images to be
rebuilt and never denotes a second command. On a machine where the images already exist,
`docker compose up --wait` alone is enough.

Loading the seed fixtures is a data operation, not a start step:

```bash
docker compose exec -T api npm run seed
```

That command is invoked by `./verify.sh` and by an operator; it is not required to start the stack.
After a plain `up --wait` the database is empty on purpose, because the empty state is part of the
frontend contract (§6) and the vertical slice builds its board and columns from nothing.

Running the API from a host Node.js, or the frontend through `vite dev`, is a development
convenience and never the Definition of Done. The Definition of Done is the Compose stack.

The boundaries are the seams the tests use:

- `repo/` is the only place that contains SQL; `routes/` is the only place that knows about HTTP
  statuses and request bodies; `errors.ts` is the only place that maps a declared error code to a
  status.
- `repo` functions accept a `Queryable` (the pool, or a transaction client) instead of opening their
  own connection. That is what lets a route compose several statements into one transaction without

- `web/src/lib/state.ts` is pure: `(state, event) => state`, with no `fetch` and no DOM reference.

- `web/src/lib/api.ts` is the only module that calls `fetch`, and the only one that turns a non-2xx
  body into a typed `ApiError { code, message, status }`.
- Dependencies point one way: `routes → repo → db`, `routes → errors`, and on the web side
  `components → state`, `components → api`.
- No global mutable state except the single pg pool created in `db/pool.ts`.

## 4. Data model, migrations and the ordering invariant

### Schema

Table names are plural and stable; JSON field names are singular and stable. `columns` is a reserved
word in SQL, so the table is `board_columns` while every JSON body says `columns`:

```sql
CREATE TABLE schema_migrations (
  version    INTEGER PRIMARY KEY,
  name       TEXT NOT NULL,
  applied_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE boards (
  id         UUID PRIMARY KEY,
  title      TEXT NOT NULL CHECK (length(btrim(title)) BETWEEN 1 AND 120),
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE board_columns (
  id       UUID PRIMARY KEY,
  board_id UUID NOT NULL REFERENCES boards(id) ON DELETE CASCADE,
  title    TEXT NOT NULL CHECK (length(btrim(title)) BETWEEN 1 AND 120),
  position INTEGER NOT NULL CHECK (position >= 0),
  UNIQUE (board_id, position)
);

CREATE TABLE tasks (
  id          UUID PRIMARY KEY,
  column_id   UUID NOT NULL REFERENCES board_columns(id) ON DELETE CASCADE,
  title       TEXT NOT NULL CHECK (length(btrim(title)) BETWEEN 1 AND 200),
  description TEXT NOT NULL DEFAULT '' CHECK (length(description) <= 2000),
  position    INTEGER NOT NULL CHECK (position >= 0),
  created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
  UNIQUE (column_id, position)
);

CREATE INDEX tasks_by_column_position ON tasks (column_id, position);
```

`0001_init.sql` creates `boards`, `board_columns`, `tasks` with `UNIQUE (board_id, position)` and
`UNIQUE (column_id, position)`. `0002_task_details.sql` adds `tasks.description` with its 2000
character `CHECK`, the index above, and nothing else. Two ordered files exist so that schema
evolution is exercised rather than a single create-everything script: a database built from
`0001` alone is not the final schema, and the runner proves that by applying both in order.

Rules:

- ids are UUIDs: the API generates a version 4 UUID for every row it creates, and the seed uses
  fixed literals, so an id is portable between two databases and no sequence is part of the
  contract;
- deletion cascades: deleting a board deletes its columns and their tasks; deleting a column
  deletes its tasks;
- `created_at` is recorded but never exposed in a response body and never part of the seed digest,
  so nothing deterministic depends on the clock;
- uniqueness and the non-negative position are enforced by the database, not only by application
  checks: a write that would duplicate a position fails the transaction.

### Migrations

- ordered `.sql` files in `api/db/migrations/`, applied in filename order by `db/migrate.ts` at
  process start, before the HTTP listener is opened;
- each file runs inside its own transaction and is recorded in `schema_migrations` with `version`
  taken from the filename prefix and `name` set to the filename;
- a file with a version already recorded is skipped; an applied migration is never edited after the
  fact;
- if `schema_migrations` holds a version with no matching file on disk, the process exits with a
  message naming the missing version and never serves `/healthz`; a silent schema drift is not an
  option;
- startup prints one line per newly applied migration,
  `migration applied version=2 name=0002_task_details.sql`, and one summary line
  `migrations pending=0 applied=2`;
- a migration that throws rolls back, leaves `schema_migrations` unchanged and makes the process
  exit non-zero;
- `/healthz` reports `schema_version` equal to the highest applied version.

### The ordering invariant

This is the benchmark's hard part, and it is stated as an invariant: the mechanism that keeps it is
the implementer's choice.

1. Positions are 0-based integers and are dense on commit: for every column the sorted task positions
   are exactly `0..n-1`; for every board the sorted column positions are exactly `0..m-1`.
2. Uniqueness is enforced by the schema — `UNIQUE (column_id, position)` and
   `UNIQUE (board_id, position)` — so an application bug cannot commit two rows at one position.
3. Reads are gap-tolerant: a read orders by `position, id` and never assumes denseness. A committed
   write restores denseness for the affected column and, for a cross-column move, for both the
   source and the target column.
4. Every mutating request is one transaction. After a commit the invariant holds; after a rollback
   neither the source nor the target state has changed. A partially applied renumbering is never
   visible to a concurrent reader.
5. A move carries `target_column_id` and `target_position`, where `target_position` is the 0-based
   index the task must occupy after the move, in the target column with the task already removed
   from wherever it was. `target_position == len(target column)` appends. Any other value is
   `400 invalid_field` and changes nothing.
6. A move to the same column and the index the task already occupies is a no-op: `200` with the
   unchanged task, and the transaction writes nothing.
7. Concurrent writes cannot duplicate a position, lose a task or produce a gap. Moves that touch the
   same column serialise. Whether that is a row lock on the column, a `SELECT … FOR UPDATE` over the
   column's tasks, or a serialisable transaction with a bounded internal retry is not part of the
   contract; the invariant and the concurrency test of §9 are. Contention is never surfaced to the
   client: the API does not return `409`.
8. Deleting a task or a column renormalises the remaining positions inside the same transaction.

## 5. HTTP API contract

The API serves its routes at its own root. nginx publishes them under `/api`, which is the base path
the browser uses; a request to `GET /api/boards` on port 8080 reaches `GET /boards` on the API.
Bodies are JSON and errors are JSON, never HTML: nginx is configured with
`proxy_intercept_errors off`, so an API error reaches the browser as the API wrote it.

| method | path (browser base `/api`) | purpose |
|---|---|---|
| `GET` | `/healthz` | liveness plus applied schema version (API root only, not proxied; printed by `npm run health`) |
| `GET` | `/boards` | every board with its column and task counts |
| `POST` | `/boards` | create a board |
| `GET` | `/boards/{boardId}` | one board with its columns and their tasks, ordered |
| `PATCH` | `/boards/{boardId}` | rename a board |
| `DELETE` | `/boards/{boardId}` | delete a board with its columns and tasks |
| `POST` | `/boards/{boardId}/columns` | create a column, appended or at a position |
| `PATCH` | `/columns/{columnId}` | rename a column, or move it inside its board |
| `DELETE` | `/columns/{columnId}` | delete a column and its tasks |
| `POST` | `/columns/{columnId}/tasks` | create a task, appended or at a position |
| `PATCH` | `/tasks/{taskId}` | rename a task or edit its description |
| `DELETE` | `/tasks/{taskId}` | delete a task |
| `POST` | `/tasks/{taskId}/move` | atomic move to a target column and position |

Lists are complete: there is no pagination, no cursor and no page parameter anywhere in the
contract. The datasets are bounded — the seed is two boards, seven columns, eighteen tasks — and a
model that invents a page parameter has misread the contract.

`GET /healthz` answers `200 {"status":"ok","schema_version":2}` when the database round trip
succeeds, and `503 {"status":"degraded","database":"unreachable"}` when it fails; it is the only
endpoint that does not use the error shape below.

### Bodies

Board summary, as returned by `GET /boards`:

```json
{"boards": [{"id": "6f1d5a2c-1b1f-4a3e-9a03-1b1f4a3e9a03", "title": "Sprint 42",
             "column_count": 4, "task_count": 12}]}
```

Boards are sorted by `title`, then by `id`, so the list order is total and not insertion-dependent.

Board detail, as returned by `GET /boards/{boardId}` and inside `POST /boards` responses:

```json
{
  "id": "6f1d5a2c-1b1f-4a3e-9a03-1b1f4a3e9a03",
  "title": "Sprint 42",
  "columns": [
    {"id": "8a2b…", "title": "To do", "position": 0,
     "tasks": [{"id": "c41e…", "column_id": "8a2b…", "title": "Write the migration",
                "description": "", "position": 0}]},
    {"id": "9b3c…", "title": "Done", "position": 1, "tasks": []}
  ]
}
```

A column object is always `{id, title, position, tasks}`; a task object is always
`{id, column_id, title, description, position}`. The same two shapes are used by every endpoint, so a
client never needs a second decoder.

Requests:

| endpoint | body |
|---|---|
| `POST /boards` | `{"title": "Sprint 42"}` |
| `PATCH /boards/{id}` | `{"title": "Sprint 43"}` |
| `POST /boards/{id}/columns` | `{"title": "Done"}` or `{"title": "Done", "position": 1}` |
| `PATCH /columns/{id}` | `{"title": "Doing"}` or `{"position": 2}` or both |
| `POST /columns/{id}/tasks` | `{"title": "Write the migration"}` with optional `description` and `position` |
| `PATCH /tasks/{id}` | `{"title": "…"}` and/or `{"description": "…"}` |
| `POST /tasks/{id}/move` | `{"target_column_id": "9b3c…", "target_position": 0}` |

When `position` is absent on a create, the new row is appended at the end. When it is present it is
an index in `0..n` of the destination column, or of the board for a column. `PATCH /tasks/{id}`
accepts `title` and `description` only; a `position` or `column_id` field there is
`400 invalid_field` and names the move endpoint in its message, because one concept has one
spelling.

Statuses: `200` for a read or an update, `201` for a create, `204` for a delete. A move answers
`200` with the moved task object, so the client can confirm the result without a second request; a
repeated identical move is a no-op that answers `200` with the same object.

### Errors

Every error body has one shape:

```json
{"error": "column_not_found", "message": "column 9b3c… does not exist"}
```

| status | code | when |
|---|---|---|
| 400 | `malformed_json` | the body is not a JSON object |
| 400 | `invalid_field` | in a body: a title is missing, blank or too long, a description is above 2000 characters, a field has the wrong type, an id is not a UUID string, a position is not an integer or is out of range, or a `PATCH` carries no accepted field |
| 400 | `invalid_id` | a path parameter is not a UUID |
| 404 | `board_not_found` | the `boardId` does not exist |
| 404 | `column_not_found` | the `columnId`, or a move's `target_column_id`, does not exist |
| 404 | `task_not_found` | the `taskId` does not exist |
| 404 | `unknown_route` | no route matches the path |
| 405 | `method_not_allowed` | the path matches and the method does not |
| 413 | `body_too_large` | the body exceeds 16 KiB |
| 415 | `unsupported_media_type` | a request with a body does not declare `application/json` |
| 500 | `internal` | an unexpected exception; logged once with the request id, and the process keeps serving |

Unknown request fields are ignored, so a client may send extra metadata. Field validation happens
before any transaction opens, so a rejected request writes nothing.

## 6. Frontend behaviour and states

One page, no router library. The query string `?board=<id>` selects a board, so a reload restores the
view without keeping state in memory: that is what makes "visible after reload" a measurement rather
than a claim. Without `?board`, the page shows the board list.

The store is a single value, produced by the pure reducer in `lib/state.ts`:

```text
{ status: "loading" | "ready" | "empty" | "error",
  boards: BoardSummary[],
  board: Board | null,
  error: { code: string, message: string } | null }
```

| status | trigger | observable |
|---|---|---|
| `loading` | first fetch of a board or of the list, or a retry | a `loading-state` region with the text `Loading board…`; mutation controls disabled |
| `empty` | the board list came back empty | an `empty-state` region with the text `No boards yet` and the create-board form |
| `error` | a request failed: a transport error, a 5xx, or a 4xx on a board id | an `error-banner` showing the error code — `network_error` for a transport failure, otherwise the API's own declared code — its message, and a `Retry` button; a previously loaded board stays visible underneath |
| `ready` | a board loaded | board heading, columns in position order, task cards in position order, each card with its move controls |

An empty column is not an error and not the page-level empty state: it is a column in `ready` that
shows `This column is empty` inside itself. `network_error` is the only error code invented on the
client; every other code in the banner comes from the API and is quoted unchanged.

Required observable surface, which is what the e2e spec asserts:

| element | contract |
|---|---|
| board list | `data-testid="board-list"`, one `board-item` per board, each a link to `?board=<id>` |
| create board form | `data-testid="new-board-form"`, a text field labelled `Board title`, a button named `Create board` |
| create column form | `data-testid="new-column-form"`, a field labelled `Column title`, a button named `Create column` |
| create task form | inside a column, a field labelled `Task title`, a button named `Create task` |
| column | `data-testid="column"`, `data-column-id` and `data-position` |
| task card | `data-testid="task-card"`, `data-task-id` and `data-position` |
| move controls | four buttons per card, named `Move <task title> up`, `… down`, `… to previous column`, `… to next column`; disabled at the boundary instead of failing |
| states | `loading-state`, `empty-state`, `error-banner` |

Ordering is asserted twice on purpose: the DOM order of `task-card` elements inside a column, and
their `data-position` values, which must be `0..n-1` in that same order.

After every mutation the client refetches the affected board and renders what the API returned; no
optimistic update is required, and no test may assume one. Layout is plain CSS with the system font
stack: no downloaded font, no remote image, no icon library — the offline constraint applies to the
frontend as much as to the backend.

## 7. Deterministic seed

`api/db/seed/fixtures.json` is a committed file with fixed ids:

- board `Sprint 42` (`11111111-1111-4111-8111-111111111111`) with columns `Backlog`, `To do`,
  `In progress`, `Done` at positions 0–3 and 12 tasks;
- board `Onboarding` (`22222222-2222-4222-8222-222222222222`) with columns `Not started`, `Doing`,
  `Done` at positions 0–2 and 6 tasks.

Total: 2 boards, 7 columns, 18 tasks. One task title carries a non-ASCII character and one carries a
double quote, so encoding is exercised in both directions.

`npm run seed` inserts the fixtures and prints one line per board plus a total:

```text
seed board="Sprint 42" columns=4 tasks=12 digest=sha256:…
seed board="Onboarding" columns=3 tasks=6 digest=sha256:…
seed total boards=2 columns=7 tasks=18 digest=sha256:…
```

Each digest is the SHA-256 of canonical JSON: boards sorted by id, columns sorted by position, tasks
sorted by position, fields `id`, `title` and `position` (plus `description` for tasks). No timestamp
and no clock value enters the digest, so it is a property of the fixtures and not of the machine.

Requirements:

- the same fixtures on a fresh volume produce the same digests on any host, on any run;
- the command is idempotent: a second run inserts nothing, leaves the row counts unchanged and prints
  the same digests, because it upserts on the primary keys and never depends on insertion order;
- the command refuses to run when the applied schema version is below the highest migration on disk,
  and says so instead of failing on a missing column;
- an id left over from an earlier fixture revision is an error, not silently ignored: the seed
  reports the difference between the fixtures and the database instead of merging.

```yaml
    healthcheck: fetch http://127.0.0.1:3000/healthz (interval 2s, timeout 3s, retries 30, start_period 15s)
  web:
    build: {context: ./web, target: runtime}
    depends_on: {api: {condition: service_healthy}}
    ports: ["8080:80"]
    healthcheck: wget -qO- http://127.0.0.1/healthz (interval 2s, timeout 3s, retries 30, start_period 10s)
  web-e2e:
    profiles: ["e2e"]
    build: {context: ./web, target: e2e}
    depends_on: {web: {condition: service_healthy}}
    environment: [BASE_URL=http://web]
volumes:
  taskboard-db:
```

Rules:

- **exactly three long-running services** are started by the start command: `db`, `api`, `web`.
  `web-e2e` is a tool service behind the `e2e` profile, has no published port, and is started only by
  `./verify.sh`; it is not part of the running stack and does not count as a fourth node of the
  application;
- `docker compose up --wait` returns 0 only when all three are healthy. Because `api` is only started
  after `db` is healthy, and `web` only after `api` is healthy, the first browser request cannot hit
  an unmigrated database or an API without a pool;
- only `web` publishes a host port. `api` and `db` are reachable only on the Compose network: the
  contract between processes is a service name and a port, not a host port, and the e2e check is what
  proves the frontend really consumes the API;
- the API applies migrations at startup, before opening its listener, so "healthy" implies "schema at
  the latest version"; `/healthz` answers `503` with `{"status":"degraded","database":"unreachable"}`
  when the database round trip fails, which is what makes the health gate meaningful;
- nginx serves the frontend's own `/healthz` as a static `200` — that path is what its Compose
  healthcheck probes — and proxies `/api/`, with `proxy_intercept_errors off` and a 16 KiB body
  limit aligned with the API's own limit. A request above that limit is answered by nginx itself,
  through `error_page 413` pointing at a small named location that returns
  `{"error":"body_too_large","message":"request body above 16 KiB"}` with `Content-Type:
  application/json`, so the browser never sees an HTML error page;
- teardown is `docker compose down -v`: the named volume goes away, so a leaked volume cannot make a
  later run pass. `./verify.sh` always ends there, including on failure.

## 9. Test strategy and required coverage

Seam A applies: every check asserts external behaviour. API tests assert HTTP statuses, HTTP bodies
and rows read back through the API; they never assert ORM calls, query strings or internal function
names. The project's own suite (Seam D) is:

- **API tests in the container, against the containerised database.** `npm run test:api` runs
  Vitest inside the `api` container. Its global setup creates a separate database `taskboard_test`
  from the same migration files, starts the built server on port 3100, and drops the database at the
  end. Each test truncates the tables it needs before it runs. There is no mocked database, no
  in-memory substitute and no skip when the database is missing: an unreachable database fails the
  run, and one test queries `version()` on the connection it was given and asserts it reports
  PostgreSQL 16, so a substitute engine cannot pass unnoticed.
- **Ordering and concurrency tests.** A scripted sequence of 200 moves driven by a committed PRNG
  (mulberry32, seed 42) asserts the §4 invariant after every move. A concurrency test issues 8
  parallel moves that target the same position in the same column, repeated for 20 iterations, then
  asserts: the task multiset is unchanged, every position in `0..n-1` is occupied exactly once, no
  request answered `409`, and no request answered `5xx`. A reader loop issuing `GET /boards/{id}`
  during those moves never observes a gap or a duplicate.
- **Frontend unit tests.** Vitest over `lib/state.ts`, `lib/moves.ts` and `lib/api.ts` only: reducer
  transitions, boundary move availability, and error mapping with a stub `fetch`. No jsdom, no
  component rendering.
- **One headless end-to-end path.** `web/e2e/slice.spec.ts` with Playwright and Chromium, driven
  against the running stack through `http://web` on the Compose network. The file holds four tests:
  `vertical slice`, `empty and loading states`, `error state for an unknown board` and
  `api unreachable`. `./verify.sh` runs it twice — `--grep-invert "api unreachable"` while the stack
  is up, then `--grep "api unreachable"` after stopping the API — so there is one path, exercised in
  two states. The tests inside the file run in that order, and the first pass runs against a
  database no earlier step has written to — the API suite of step 2 of `## Verify` owns the separate
  `taskboard_test` database — so the empty state is measured, not arranged. Assertions are on DOM
  presence, text, attributes and ordering; screenshots, pixel comparisons and any visual judgement
  are forbidden. The spec fails on any `console` error or uncaught page error.
- **Table-driven tests.** The error table of §5 is covered row by row by a parametrised test whose
  rows carry their own expected status and code, so a missing case names itself.
- Test names state behaviour and numbers: `move to position 4 of a 4-task column appends`,
  `8 concurrent moves to position 0 keep positions dense`, not `test ordering`.

### M3 — Ordering and atomic move invariants (10)

**Implement:** `repo/positions.ts` and the transactional move; renumbering on create, delete and
column reorder; the same-column no-op; the position validation.

**Acceptance:**

- creating a task at position 0, in the middle and at the end of a column leaves positions
  `0..n-1` in that order, and the response positions match a read-back;
- a move within a column up and down shifts the siblings deterministically, and the round trip
  returns to the original order;
- a move across columns renumbers both the source and the target column, and the task count of the
  board is unchanged;
- `target_position == len(target column)` appends; `len + 1` and `-1` are `400 invalid_field` and
  change nothing;
- a move to the same column and position is a `200` no-op that writes nothing: the test compares the
  board detail before and after and the equal values include every position;
- deleting a task or a column renormalises the remaining positions in the same transaction;
- the scripted 200-move sequence holds the §4 invariant after every move;
- the concurrency test of §9 passes for 20 iterations: 8 parallel moves, dense unique positions,
  unchanged task multiset, no `409`, no `5xx`;
- a reader loop during the concurrency test never observes a gap or a duplicate;
- no endpoint ever answers `409`.

**Verify:**


## 12. Operating instructions for the development agent

- Build the stack first and keep it runnable: a `compose.yaml` that comes up healthy is worth more
  than any endpoint, because nothing else can be measured without it.
- Work one milestone at a time. M0 is the only milestone whose omission blocks everything else; M2
  and M3 are the two that a partial implementation most often fakes, so write their tests before
  their handlers.
- Keep the database the only source of truth. No process keeps board state in memory, no cache
  decides an order, and no endpoint answers from a copy it built earlier.
- Never renumber positions in application code alone while a constraint disagrees: the transaction
  owns the whole column, not a single row.
- Write the test that names the behaviour before the handler that satisfies it, and keep the
  assertions on HTTP and on the DOM. If a test needs to know about a query or a private function,
  the seam is wrong.
- Keep the error codes of §5 exactly as declared. The frontend switches on them, the table-driven
  test reads them, and `verify.json` details quote them.
- Keep the frontend dependencies to Svelte, Vite and TypeScript. A component library, a router, a
  state library or a CSS framework adds build surface without adding a scored behaviour.
- When frontend and backend disagree, the plan decides: the API contract of §5 is the interface, not
  whatever happens to be implemented first.
- Report, before declaring a milestone done: changed files, commands run, test results, the slice
  evidence and residual risks.

## Verify

`./verify.sh` is the single verification entry point: non-interactive, timeout 600 s, exit 0 if and
only if every milestone passed. Sequence:

1. `docker compose up --wait --build` — three services healthy, migrations applied on the empty
   volume, `npm run health` reporting `schema_version: 2`, `GET /api/boards` empty. Failure here
   fails `M0` and stops the steps that need the stack, while `verify.json` is still written.
2. `docker compose exec -T api npm run test:api` — the whole API suite against the containerised
   PostgreSQL: migrations and constraints, CRUD and errors, ordering and moves, concurrency, seed.
   The suite owns the separate `taskboard_test` database, so it leaves the stack's `taskboard`
   database untouched.
3. `docker compose --profile e2e run --rm web-e2e npx playwright test --grep-invert "api
   unreachable"` — the empty and loading states, then the slice path, then the error state for an
   unknown board, in that file order and against a database nothing has written to yet.
4. `docker compose exec -T api npm run seed` twice, the two outputs compared line by line; then
   `docker compose down -v`, a second `up --wait --build` and a third seed run whose digests are
   compared with the first: two fresh volumes must produce identical digests.
5. `docker compose stop api`, then `--grep "api unreachable"`, then `docker compose start api` and a
   wait for the health gate: the error state is measured with the API genuinely down.
6. `scripts/emit_verify.mjs` maps the collected evidence onto `M0`–`M7` and writes `verify.json` next
   to `verify.sh`: `schema: 1`, `benchmark: "taskboard"`, every milestone id exactly once with `pass`
   and a `detail` naming the evidence, plus `notes` with the wall clock of the run.
7. `docker compose down -v` — always, through a trap, also on failure, interrupt or timeout.

Milestone evidence, so a `pass` is never a judgement call:

| id | passes when |
|---|---|
| `M0` | the stack came up healthy, `npm run health` reported schema version 2, and the slice test passed |
| `M1` | the migration and constraint tests passed and a restart kept the data |
| `M2` | the CRUD and error-table tests passed, including the proxy's JSON 404 |
| `M3` | the ordering, move and concurrency tests passed with no `409` and no `5xx` |
| `M4` | the state tests passed, including the error banner with the API stopped |
| `M5` | the seed digests matched within the first run and across two fresh volumes |
| `M6` | the API suite ran with zero skips against the container database, and the e2e spec passed |
| `M7` | steps 1–6 all ran and `verify.json` was written with the eight ids |

Budget, so a cold run is not a surprise: image build ≤ 300 s, API suite ≤ 120 s, e2e ≤ 120 s,
teardown ≤ 30 s. The 600 s limit is the contract; these numbers are the allocation of a reference
run and may shift with the host.

Determinism is asserted, not assumed: `./verify.sh` compares seed digests across two fresh volumes
and the API suite compares board details before and after a same-position move.
