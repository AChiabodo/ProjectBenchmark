# Plan — Kotlin Desktop: an expense tracker on the JVM, no Android SDK

## 1. Goal and scope

Build a small desktop expense tracker that really starts, really writes its data to disk and really
shows that data again after a restart — on the JVM, without the Android SDK, without an emulator and
without a display in the verification path. The difficulty is not volume: it is the seam between a
domain that must be checkable by headless JVM tests, a persistence layer that treats its own file as
untrusted input, and a desktop UI thin enough that no business rule can hide inside it.

The application is ordinary on purpose. Every rule below is stated as data — categories, bounds,
error codes, ordering, file layout — so "correct" is a property of the text and not a matter of
taste. Nothing is downloaded at runtime, no service is contacted, and the only file the application
touches is its own local store.

### Final functionality

- a Gradle build with a committed wrapper and a committed dependency lockfile, two modules, and a
  single `./gradlew run` start command;
- a domain with a declared entity (`Expense`), a closed category set, declared validation rules for
  the raw form text, and declared error codes;
- a local store behind an interface: a versioned UTF-8 text file with a schema header, atomic
  replace on write, and a declared corrupt-store path that refuses to lose data silently;
- a Swing desktop UI with an expenses view (insert, list, edit, delete) and a report view, wired to
  headless-testable presenters;
- a report with declared aggregates per category and per month over an inclusive date range;
- declared empty, loading, validation-error and store-error states, each with an exact text;
- a JVM test suite that runs headless, with no display, no network and no sleeps;
- a `--smoke` mode that boots the real wiring without creating a window, so verification never
  launches a GUI;
- `./verify.sh` writing `verify.json` with every milestone id of `meta.json`.

### Non-goals

Multiple accounts or users, budgets, shared or synced data, imports (CSV, bank feeds), currency
conversion, multiple currencies, refunds and negative amounts, recurring expenses, attachments,
receipts, encryption of the store, a migration from schema 1 to a later schema, undo/redo,
localisation, theming, animations, drag and drop, keyboard shortcuts beyond `Enter` and `Delete`,
tray icons, notifications, packaging, installers, publishing, CI and release automation, Android
with an emulator or a device, and any UI automation in the suite (see § 9).

The store is a single file and the application is single-process. That is a decision, not a gap: a
second writer, a file lock protocol or a database would each be a different benchmark.

### The Android variant is a stretch goal and is not scored

The same domain could ship as an Android application. That variant is **declared and unscored**, for
one reason: a real Android build needs `cmdline-tools`, a platform, build-tools and a Gradle plugin
that resolves from a repository this host does not use, which is a multi-gigabyte installation and
not a pinned build-time dependency. Without an emulator the check would shrink to `assembleDebug`
plus JVM unit tests, which measures the SDK download, not the application.

- What the stretch goal would be: an `:android` module that applies the Android Gradle plugin, calls
  the same `:core` domain and store, and is validated only by a debug build plus JVM unit tests.
- What is required here instead: `:core` stays free of `java.awt`, `javax.swing` and every other
  desktop-only API, so the stretch goal is a new module and not a redesign. That property is scored
  (M3, architecture test), the Android build is not.
- What no milestone depends on: no id in `meta.json` is weighted by Android work, `verify.sh` never
  invokes an Android task, and a host without any Android SDK cannot fail a single milestone. The
  Android module is not listed in `settings.gradle.kts`, so `./gradlew build` cannot reach it.

## 2. Locked technical decisions

```text
Language:    Kotlin 2.0.21, JVM target 21, Kotlin/JVM plugin, two modules
UI toolkit:  Swing and AWT from the JDK — the plan picks Swing, so there is no UI
             dependency to download and nothing to pin beyond the JDK
Store:       one versioned UTF-8 text file, java.nio.file only, no database driver
Money:       integer cents in a Long; no Double and no BigDecimal anywhere
Dates:       java.time.LocalDate, ISO yyyy-MM-dd, no clock inside the domain
Tests:       JUnit Jupiter 5.11.3 on the JVM, headless, no mocks, no sleeps
Build:       Gradle 8.10.2 from the committed wrapper, dependency locking on
```

**Why Swing and not Compose Desktop.** Compose Desktop pulls the Compose compiler plugin and
Skiko's native binaries, and it cannot be started without a graphics surface, which would make the
headless smoke check of § 8 impossible. Swing ships with the JDK: the build downloads nothing for
the UI, the core module can be proven free of UI imports, and the presenters hold every decision
that a test could otherwise only reach through pixels.

**Why a text file and not an embedded database.** The store must be inspectable in a diff, testable
without a driver, and corruptible on purpose. A versioned line format gives all three. The format is
declared in § 5, and the corrupt-store path is a scored behaviour with a test per corrupt case.

### Modules

```text
:core   domain, validation, reports, the ExpenseStore port, the file store and the
        in-memory store; dependencies: none beyond the Kotlin standard library
:app    Swing shell, presenters, composition root, argument parsing, exit codes;
        depends on :core, and on AWT/Swing from the JDK
```

`:core` cannot see Swing because it has no dependency that would provide it, and `:app` cannot be
reached from `:core` because the dependency direction is one-way. The layering is a build fact, not
a convention that a review has to police.

### Pinned dependencies

Every build-time dependency is pinned; nothing is resolved at runtime.

| item | pin | where |
|---|---|---|
| Kotlin plugin | `org.jetbrains.kotlin.jvm` version `2.0.21`, exact | `build.gradle.kts` at the root, shared by both modules |
| Kotlin standard library | the `2.0.21` artefact the plugin contributes; never declared by hand | `:core`, `:app` |
| JVM | toolchain 21 (`jvmToolchain(21)`), explicit in both modules | root `build.gradle.kts` |
| Gradle | `8.10.2`, `distributionSha256Sum` set, wrapper jar and scripts committed | `gradle/wrapper/gradle-wrapper.properties`, `gradlew`, `gradlew.bat` |
| JUnit Jupiter | `org.junit.jupiter:junit-jupiter:5.11.3`, exact, test configuration only | `:core/build.gradle.kts`, `app/build.gradle.kts` |
| JUnit platform launcher | `org.junit.platform:junit-platform-launcher:1.11.3`, exact, test runtime only | both modules |
| Dependency locks | `gradle.lockfile` per module, committed | `core/gradle.lockfile`, `app/gradle.lockfile` |
| UI toolkit | Swing and AWT from the JDK 21 runtime — no third-party artefact | `:app` |
| Store | `java.nio.file` and `java.time` from the JDK — no database driver, no JSON library | `:core` |

Rules that make the pins real:

- version strings are exact. No `5.+`, no `latest.release`, no dynamic version and no SNAPSHOT;
- `dependencyLocking { lockAllConfigurations() }` is on in both modules, so a transitive version that
  changes without the lockfile changing fails the build instead of resolving silently;
- both `gradle.lockfile` files and the wrapper are deliverables, committed with the project, and a
  build that needs an artefact absent from them fails `M0`;
- `--offline` is a development convenience, not a requirement: the first build may fetch the Kotlin
  plugin, the Kotlin standard library and JUnit from the repositories `settings.gradle.kts` declares,
  and every one of those fetches is pinned by version and by lockfile.

### Commands — exactly one of each

```bash
./gradlew run                        # the single start command: the desktop application
./verify.sh                          # the single verification command
```

`./gradlew run` opens the window with the default store. `--store PATH` may be passed through
`--args="--store PATH"`; it is an argument of the same command, not a second start command. The
Gradle `smoke` task is **not** a start command: it runs the same `main` in `--smoke` mode with
`-Djava.awt.headless=true`, it belongs to `verify.sh`, and a human never needs it.

`verify.sh` is the only verification entry point. Running `./gradlew test` by hand is a development
convenience and never the Definition of Done.

## 4. Domain contract

### 4.1 The entity

```kotlin
data class Expense(
    val id: String,             // [A-Za-z0-9-]{1,36}, generated by an IdGenerator
    val date: LocalDate,        // within the bounds of § 4.4
    val amountCents: Long,      // within the bounds of § 4.3
    val category: Category,     // one of the seven of § 4.2
    val note: String            // trimmed, possibly empty, at most 120 characters
)
```

An `Expense` that exists has already been validated, so nothing downstream re-checks it: validation
happens once, when text becomes a draft (`§ 4.2`), and once more when a record is read back from a
file (`§ 5`), because a file is untrusted input. The entity carries no behaviour beyond equality.

### 4.2 Raw form text and the closed category set

The UI holds text; the domain decides. One value carries the four raw fields:

```kotlin
data class ExpenseDraft(
    val dateText: String,       // the date field, as typed
    val amountText: String,     // the amount field, as typed
    val category: Category?,    // null when nothing is selected
    val noteText: String        // the note field, as typed
)
```

`Category` is a closed enum in this declaration order, and the label is the only display name:

| constant | label |
|---|---|
| `GROCERIES` | `Groceries` |
| `TRANSPORT` | `Transport` |
| `HOUSING` | `Housing` |
| `UTILITIES` | `Utilities` |
| `LEISURE` | `Leisure` |
| `HEALTH` | `Health` |
| `OTHER` | `Other` |

Categories are not user-defined and are not stored as a separate table: a category that is not in
this enum cannot exist, and the file format stores the constant name.

### 4.3 Money: integer cents

`amountCents` is a `Long` count of cents. There is no `Double`, no `BigDecimal` and no rounding mode
anywhere in the project, so no value can drift and no equality test depends on floating point.

Parsing `amountText`, in this order:

1. `amountText.trim()` is matched against `^[0-9]{1,7}(\.[0-9]{1,2})?$`. Nothing else is accepted:
   no sign, no thousands separator, no exponent, no leading or trailing decimal point, no space
   inside. A mismatch is `amount.format`.
2. The integer part is parsed as a `Long`, the fraction part (absent, one digit or two) is
   right-padded with `0` to two digits, and the value is `integerPart * 100 + fractionPart`. Leading
   zeros are legal: `007.50` is 750 cents.
3. The value must be at least 1 cent and at most `100000000` cents (1,000,000.00). Outside the
   bounds is `amount.range`.

Formatting `formatCents(cents: Long): String` is fixed, because the UI and the report both show it
and tests compare text:

| cents | text |
|---:|---|
| `1` | `0.01` |
| `5` | `0.05` |
| `1234` | `12.34` |
| `100000` | `1000.00` |
| `100000000` | `1000000.00` |

Always two fraction digits, never a grouping separator, never a currency symbol, never a
locale-dependent formatter. A negative input is an implementation defect and the tests pin that the
domain never produces one.

### 4.4 Dates

`dateText` is parsed with `DateTimeFormatter.ISO_LOCAL_DATE` in strict mode, so `yyyy-MM-dd` with a
four-digit year, a two-digit month and a two-digit day, and no other shape. A text that does not
parse, or parses to an impossible calendar date, is `date.format`: `2026-02-30`, `26-01-01`,
`2026-1-5`, `2026/01/05` and the empty string all fail this way.

The accepted range is `2000-01-01` to `2100-12-31` inclusive. Outside it is `date.range`. The range
is absolute rather than relative to today, so the suite needs no clock and no test becomes flaky at
midnight.

### 4.5 Notes

The note is `noteText.trim()` and is stored trimmed.

- At most 120 characters, measured by Kotlin `String.length`, so the count is UTF-16 code units and
  is reproducible. Longer is `note.length` (an emoji counts as two, which is declared, not hidden).
- No ISO control character, checked with `Character.isISOControl`. That rejects tab, newline, a bare
  CR and the C0 range in one rule, is `note.character`, and is what makes the tab-separated file
  format of § 5 unambiguous without an escaping scheme.
- Empty is legal: a note is optional. Non-ASCII text is legal and is written as UTF-8.

### 4.6 Validation and error codes

`Validation.validate(draft): List<DomainError>` is the only validator. It reports **at most one
error per field**, in the field order date, amount, category, note, so a list of errors is
deterministic and a form can focus the first one.

```kotlin
data class DomainError(val field: Field, val code: String, val detail: String)
enum class Field { DATE, AMOUNT, CATEGORY, NOTE, ID, RANGE, STORE, SELECTION }
```

| code | field | condition |
|---|---|---|
| `date.format` | `DATE` | the date text is not a strict `yyyy-MM-dd` calendar date |
| `date.range` | `DATE` | the date is outside `2000-01-01` … `2100-12-31` |
| `amount.format` | `AMOUNT` | the amount text does not match the pattern of § 4.3 |
| `amount.range` | `AMOUNT` | the parsed amount is below 1 cent or above 100,000,000 cents |
| `category.missing` | `CATEGORY` | no category is selected |
| `note.length` | `NOTE` | the trimmed note is longer than 120 characters |
| `note.character` | `NOTE` | the note contains an ISO control character |
| `id.duplicate` | `ID` | `add` receives an id that already exists in the store |
| `id.unknown` | `ID` | `update` or `delete` names an id that does not exist |
| `selection.missing` | `SELECTION` | an edit or a delete is attempted with no selected row (§ 7.4) |
| `range.inverted` | `RANGE` | a report's `from` is after its `to` |
| `store.corrupt` | `STORE` | the store reported a corrupt or unsupported file; `detail` names path and line |
| `store.io` | `STORE` | reading or writing the store failed; `detail` names the path |

The `code` is the contract: tests assert codes and fields, never message wording. The `detail`
string is the implementation's own text, chosen once, shown to the user, and never parsed.

### 4.7 Service operations and outcomes

```kotlin
sealed interface Outcome<out T> {
    data class Ok<T>(val value: T) : Outcome<T>
    data class Invalid(val errors: List<DomainError>) : Outcome<Nothing>
    data class Failed(val error: DomainError) : Outcome<Nothing>
}

class ExpenseService(store: ExpenseStore, ids: IdGenerator) {
    fun add(draft: ExpenseDraft): Outcome<Expense>
    fun update(id: String, draft: ExpenseDraft): Outcome<Expense>
    fun delete(id: String): Outcome<Unit>
    fun list(): List<Expense>
    fun report(from: LocalDate, to: LocalDate): Outcome<Report>
}
```

| operation | success | failure |
|---|---|---|
| `add` | `Ok(expense)` with a generated id, validated and written | `Invalid(field errors)`, `Failed(id.duplicate)`, `Failed(store.io)` |
| `update` | `Ok(expense)` validated and written | `Invalid(field errors)`, `Failed(id.unknown)`, `Failed(store.io)` |
| `delete` | `Ok(Unit)` written | `Failed(id.unknown)`, `Failed(store.io)` |
| `list` | the current snapshot in display order | it cannot fail: the snapshot was loaded successfully at open |
| `report` | `Ok(report)` of § 6 | `Failed(range.inverted)` |

Snapshot discipline, and it is scored: the service holds the loaded list. A mutation validates,
applies to a copy, writes the whole file through the store, and only after a successful write
publishes the copy. A failed write leaves the file and the snapshot unchanged, so the UI can never
show an item that is not on disk.

`IdGenerator` is `fun interface IdGenerator { fun next(): String }`; the application supplies
`UUID.randomUUID().toString()`, and tests supply a scripted sequence, so no test depends on a random
id.

### 4.8 Display order

`list()` returns every expense ordered by `date` descending. Expenses sharing a date keep insertion
order: the order in which they appear in the store, with a new expense appended. The sort is stable
and the tie-break is declared, so two implementations that agree on the rules produce the same list.

## 5. Persistence contract

### 5.1 The file

The store is one UTF-8 text file. Its default path is
`System.getProperty("user.home")/.kotlin-desktop/expenses.tsv`; `--store PATH` overrides it. Its
content is exactly:

```text
schema=1
<id>\t<yyyy-MM-dd>\t<amountCents>\t<CATEGORY>\t<note>\n
```

- line 1 is the literal string `schema=1`, with no spaces and no BOM;
- every following line is one record: five tab-separated fields in that order, with `amountCents` a
  plain decimal integer with no sign and no grouping, `CATEGORY` a constant of § 4.2, and the note
  last so that an empty note is a trailing tab and the line still has five fields;
- the terminator is a single `\n` on every line, the last one included;
- the file is written whole and never appended to.

### 5.2 Reading, and what counts as corrupt

```kotlin
interface ExpenseStore {
    fun load(): LoadOutcome
    fun save(expenses: List<Expense>): SaveOutcome
}

sealed interface LoadOutcome {
    data class Ready(val expenses: List<Expense>) : LoadOutcome
    data class Corrupt(val path: String, val line: Int, val reason: String) : LoadOutcome
    data class UnsupportedSchema(val path: String, val line: Int, val version: Int) : LoadOutcome
    data class IoFailure(val path: String, val reason: String) : LoadOutcome
}

sealed interface SaveOutcome {
    data object Saved : SaveOutcome
    data class IoFailure(val path: String, val reason: String) : SaveOutcome
}
```

`path` is the file path as the application resolved it; `line` is 1-based, where line 1 is the schema
line. The outcome kind, the path and the line number are the contract; `reason` is the
implementation's text, shown to the user and asserted for its line number, not for its wording.

| condition | outcome | line |
|---|---|---|
| the file does not exist | `Ready(emptyList())` — first run, not corruption | — |
| the file exists with zero bytes | `Corrupt` | 1 |
| line 1 is not exactly `schema=` followed by digits | `Corrupt` | 1 |
| line 1 declares a version other than `1` | `UnsupportedSchema(version)` | 1 |
| any line contains a `\r` | `Corrupt` | that line |
| a blank line | `Corrupt` | that line |
| a record line whose field count is not five | `Corrupt` | that line |
| a field that is not a valid value under § 4.1–§ 4.5 | `Corrupt` | that line |
| a duplicate id | `Corrupt` | the second occurrence |
| the file cannot be read at all | `IoFailure` | — |

Every record is validated on load against the same bounds the form uses (§ 4.1–§ 4.5): the amount
must lie within 1 and 100,000,000 cents, the date within its range, the category a constant of
§ 4.2, the note already trimmed, free of control characters and at most 120 characters long. A
hand-edited file therefore cannot smuggle an out-of-range amount or a control character into the
running application.

### 5.3 Writing

1. The parent directory is created if it is missing (`Files.createDirectories`).
2. The whole list is written to `<file>.tmp` in the same directory, with UTF-8, `\n` terminators and
   the schema header, and the channel is forced to disk.
3. The temp file is moved onto the target with `ATOMIC_MOVE` and `REPLACE_EXISTING`, so a reader
   either sees the previous file or the new one.
4. On any failure the temp file is deleted and `SaveOutcome.IoFailure` is returned; the target keeps
   its previous bytes.

Consequences that the suite asserts: the temp file does not exist after a successful save, a failed
save leaves the file byte-identical, and saving a list that was just loaded reproduces the same
bytes.

### 5.4 What the application does with a broken store

A corrupt or unsupported store is a visible state, never an empty list:

- the list presenter enters `StoreError` with the path, the line and the reason;
- add, edit and delete are disabled (`canMutate == false`), so the file cannot be overwritten by a
  first save that would hide the original;
- the status line shows `Store unavailable: <path>:<line> <reason>`;
- `--smoke` exits 3 with exactly one line on stderr and nothing on stdout (see § 8).

An `IoFailure` while reading behaves the same way with line 0 and exit 4. There is no "start empty
and lose it" path, and no automatic repair.

## 6. Report contract

### 6.1 Shape

```kotlin
data class CategoryTotal(val category: Category, val count: Int, val totalCents: Long)
data class MonthTotal(val month: YearMonth, val count: Int, val totalCents: Long)
data class Report(
    val from: LocalDate,
    val to: LocalDate,
    val count: Int,
    val grandTotalCents: Long,
    val byCategory: List<CategoryTotal>,
    val byMonth: List<MonthTotal>
)
```

### 6.2 Aggregate rules

- The range is inclusive on both ends: an expense dated `from` and one dated `to` are both included.
  A single-day report (`from == to`) is legal.
- An expense outside the range is excluded from the totals, from the per-category rows and from the
  per-month rows.
- `count` is the number of included expenses; `grandTotalCents` is the sum of their `amountCents`.
- `byCategory` has exactly one row per category with at least one included expense. Rows are ordered
  by `totalCents` descending, ties broken by § 4.2 declaration order ascending. A category with no
  expense has no row; there is no zero row.
- `byMonth` has exactly one row per `YearMonth` with at least one included expense, ordered by month
  ascending. A month inside the range with no expense has no row: gaps are not filled.
- An empty period yields `count = 0`, `grandTotalCents = 0` and two empty lists — never `null`,
  never a placeholder row.
- `from > to` is `range.inverted`, reported as `Failed`, and no report is built.
- All arithmetic is `Long` on cents. Nothing is rounded, so `grandTotalCents` equals the sum of the
  displayed rows exactly.

### 6.3 The report view

The report view is one presenter plus one tab: a header with the range and the formatted grand
total, a table of category rows (`label`, `count`, `formatCents(totalCents)`) and a table of month
rows (`yyyy-MM`, `count`, `formatCents(totalCents)`). The range fields are two `yyyy-MM-dd` texts,
defaulting to the first and last day of the current month taken from the injected
`today: () -> LocalDate`, so tests are independent of the real date. Invalid range text produces the
same error codes as the form (`date.format`, `date.range`, `range.inverted`).

## 7. Desktop UI contract

### 7.1 Layering

| layer | holds | may not hold |
|---|---|---|
| `:core` domain and store | rules, validation, aggregates, file format | any `java.awt` or `javax.swing` import |
| `ui/presenter` | state, texts, formatting of rows, focus order | any `java.awt` or `javax.swing` import, any parsing rule |
| `ui/swing` | components, layout, listeners that delegate | arithmetic, validation, file access, report computation |

Two architecture tests enforce the table: no source file under `ui/presenter` contains
`javax.swing` or `java.awt`, and no source file under `core` does either. The Swing shell is the
only code that cannot be unit-tested, and it is kept thin enough that this costs nothing: every
branch a test cares about lives one call away in a presenter.

### 7.2 States

```kotlin
sealed interface ListState {
    data object Loading : ListState
    data object Empty : ListState
    data class Ready(val rows: List<ExpenseRow>) : ListState
    data class StoreError(val path: String, val line: Int, val reason: String) : ListState
}
```

- `Loading` is the state before the store has been opened; the Swing shell renders it for the frame
  of work between construction and the first refresh.
- `Empty` is a successful load with no expense.
- `Ready` carries one row per expense in the order of § 4.8, each row already formatted:
  `date` as `yyyy-MM-dd`, `amount` as `formatCents`, `category` label, `note` as stored.
- `StoreError` carries the path, the line and the reason, sets `canMutate = false` and never
  degrades into `Empty`.

The report presenter has `Empty`, `Ready` and `StoreError` and no `Loading` state, because it is
built only after a successful open; its empty state is the empty-period text of § 7.3.

### 7.3 Exact texts

These strings are contract, because a test asserts them without a display:

| where | text |
|---|---|
| loading | `Loading expenses...` |
| empty list | `No expenses yet.` |
| empty report period | `No expenses in this period.` |
| store error | `Store unavailable: <path>:<line> <reason>` |
| status line, one row | `1 expense.` |
| status line, n ≠ 1 rows | `<n> expenses.` |

Everything else the user sees — buttons, column headers, field labels — is the implementation's
choice and is not scored.

### 7.4 The frame

One frame, two tabs, `Expenses` and `Report`.

- `Expenses`: a table (date, amount, category, note) with single-row selection, and a form with a
  date field, an amount field, a category combo and a note field, plus `Add`, `Save`, `Delete` and
  `New` buttons. `Add` submits a new draft, `Save` submits the selected row as an edit, `Delete`
  deletes the selected row, `New` clears the form and the selection.
- `Report`: two range fields, a `Refresh` button, the header line and the two tables.

Form behaviour, all decided in the presenter:

- an invalid submit keeps every typed character, exposes the errors in field order and sets
  `firstInvalidField`; the shell moves focus there and writes the error texts next to the fields;
- a valid add or edit clears the form, refreshes the rows from the service and updates the status
  line;
- `Add`, `Save` and `Delete` are enabled only when `canMutate` is true; `Save` and `Delete` also
  require a selection, and without one they return `selection.missing`.

## 8. Application process: arguments, modes, exit codes

```text
kotlin-desktop [--store PATH] [--smoke]
```

| argument | meaning |
|---|---|
| `--store PATH` | the store file; at most once; defaults to `~/.kotlin-desktop/expenses.tsv` |
| `--smoke` | boot the wiring, report readiness, exit; never creates a window and never writes |

| mode | behaviour |
|---|---|
| GUI (no `--smoke`) | opens the frame in the state of § 7.2; the process exits 0 when the frame closes normally |
| smoke (`--smoke`) | resolves the store path, opens the store, builds the service and both presenters, prints one line on stdout, exits |

The smoke mode is what makes verification headless, and it is deliberately shallow: it proves that
the process starts, that the store opens, that the wiring of § 3 is what `main` builds, and that the
process exits cleanly. It asserts nothing about pixels, and no milestone asks for more.

Smoke output, exact:

| situation | stdout | stderr | exit |
|---|---|---|---|
| store opened | `ready store=<path> expenses=<n>` and a newline, where `<n>` is the loaded count and `<path>` is `Path.toAbsolutePath().toString()` | empty | 0 |
| corrupt or unsupported store | empty | one line `store error at <path>:<line>: <reason>` | 3 |
| the store cannot be read or written at all | empty | one line `store error at <path>: <reason>` | 4 |
| usage error: unknown argument, repeated `--store`, missing value | empty | one usage line | 2 |

The `-Djava.awt.headless=true` system property is set by the Gradle `smoke` task of § 2, and the
smoke path creates no Swing or AWT object at all, so it succeeds on a host with no display.

The Gradle hooks that `verify.sh` drives, declared here so the harness and the build cannot drift:

```kotlin
// app/build.gradle.kts
tasks.test {
    useJUnitPlatform {
        (project.findProperty("testTags") as String?)?.let { includeTags(it) }
    }
}

tasks.register<JavaExec>("smoke") {
    mainClass.set("expenses.app.MainKt")
    classpath = sourceSets["main"].runtimeClasspath
    workingDir = rootProject.projectDir          // fixture paths resolve from the benchmark root
    systemProperty("java.awt.headless", "true")
    val store = project.findProperty("store") as String
        ?: throw GradleException("-Pstore=<path> is required")
    args = listOf("--smoke", "--store", store)
}
```

`-PtestTags=M0` … `-PtestTags=M5` select one milestone's tests; without the property every test runs.

## 9. Test strategy and required coverage

Every test is a JVM test in `:core` or `:app`. No test creates a `JFrame`, a `JPanel` or any other
AWT/Swing object, opens a display, sleeps, reads the network or depends on the current date. Test
doubles are hand-written: an `InMemoryExpenseStore` for the happy path, a failing store for the
error path, and a `ScriptedIdGenerator` for identity.

Test classes are annotated with the milestone tags they score (`@Tag("M0")` … `@Tag("M6")`), which is
how `verify.sh` turns one suite into one exit status per milestone. A class may carry several tags,
and **every** test class carries at least one, so the six filtered runs of `verify.sh` together
execute the whole suite and no test can pass unobserved.

| area | what is asserted | minimum cases |
|---|---|---|
| domain validation | one case per validation code of § 4.6 (`date.format`, `date.range`, `amount.format`, `amount.range`, `category.missing`, `note.length`, `note.character`), asserting code and field; at most one error per field; field order | 14 |
| amount | the parse and format tables of § 4.3, plus every rejected shape of § 4.3 | 16 |
| date and note | both bounds and both rejections per field, an empty note, a 120 and a 121 character note, tab, newline, non-ASCII | 12 |
| store | round trip, the restart of M0, byte stability, atomic replace, missing file, every corrupt case of § 5.2, `schema=2`, I/O failure | 18 |
| service | add, update, delete, duplicate id, unknown id, failed write leaves snapshot and file unchanged | 12 |
| report | totals, inclusive bounds, ordering including a tie, skipped month, empty period, single day, inverted range | 14 |
| presenters | state transitions, exact texts of § 7.3, form error order and `firstInvalidField`, selection rules, `canMutate` | 18 |
| architecture | no `javax.swing`/`java.awt` import under `ui/presenter` or under `core` | 2 |

The suite never asserts a message string of `DomainError.detail`, an internal class name, a private
function or a source location inside the implementation. It asserts codes, counts, order, bytes and
exit codes — everything a second implementation could disagree with.

## 12. Operating instructions for the development agent

- Work one milestone at a time and keep the build green after each one; M0 is the only milestone
  whose omission blocks everything else, because nothing else can be demonstrated without a project
  that starts.
- Write the test for a rule before implementing the rule, and change a rule by changing this plan
  first: the plan is the specification, the implementation follows it.
- Keep one spelling per concept. `Expense`, `ExpenseDraft`, `ExpenseStore`, `ExpenseService`,
  `Outcome`, `DomainError`, `Report`, `ListState` are the nouns of the project; a second word for one
  of them is a defect.
- Keep validation in exactly one place. If a rule is checked in the Swing shell, moved into a
  presenter, or duplicated in the store, the layering is broken even when the tests pass.
- Keep the store on the file, not in memory only. A `--smoke` run must read the same bytes a restart
  reads; an in-memory substitute that passes the suite is a false positive.
- Prefer a smaller, fully declared application over an extra feature this plan does not mention:
  currencies, budgets, imports and sync are non-goals even when they look like ten minutes of work.
- Do not adopt the Android variant. If it appears, it appears as an unlisted module that changes no
  milestone and no verify step.
- Report, before declaring a milestone done: changed files, commands run, test counts per tag, the
  smoke lines and their exit codes, and residual risks.

## Verify

`./verify.sh` is the single verification entry point: non-interactive, timeout 600 s, exit 0 if and
only if every milestone passed. No window is launched at any point. Sequence:

1. `./gradlew --no-daemon --console=plain build -x test` — compiles both modules with warnings as
   errors, resolves dependencies against the committed lockfiles and assembles. A dependency that is
   not locked, a changed pin or a compile error fails here and fails `M0`.
2. `./gradlew --no-daemon --console=plain cleanTest test -PtestTags=M0`, then `M1`, `M2`, `M3`, `M4`,

   every test class carries a tag (§ 9), these six runs execute the whole suite, and a failure only
   sinks the milestone that owns it.
3. `./gradlew --no-daemon --console=plain smoke -Pstore=tests/fixtures/seed-schema1.tsv` — the
   process starts headless, prints `ready store=… expenses=3` and exits 0, which is the
   process-level proof that the format of § 5.1 reads back. Fixture paths are relative to the
   benchmark root, which the `smoke` task of § 8 uses as its working directory.
4. `./gradlew --no-daemon --console=plain smoke -Pstore=tests/fixtures/corrupt-missing-header.tsv` —
   exits 3, writes exactly one line to stderr naming the path and line 1, and writes nothing to
   stdout; the same run against `tests/fixtures/unsupported-schema.tsv` does the same for the schema
   version.
5. `verify.sh` maps the collected evidence onto `M0`–`M6` and writes `verify.json` in the project
   root next to `verify.sh`: `schema: 1`, `benchmark: "kotlin-desktop"`, every milestone id exactly
   once with `pass` and a `detail` naming the evidence, plus `notes` with the wall clock of the run.
6. `node ../../scripts/score.mjs meta.json verify.json --exit $status` is the acceptance check of the
   file itself; it is run by the operator, not by `verify.sh`.

Milestone evidence, so a `pass` is never a judgement call:

| id | passes when |
|---|---|
