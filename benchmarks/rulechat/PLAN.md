# Plan — RuleChat: deterministic conversational service

## 1. Goal and scope

Build a conversational service whose dialogue logic is the thing being measured. RuleChat is a
rule-based NLU plus an explicit dialogue state machine over a corpus of utterances bundled in the
repository. There is no model, no embedding, no training step and nothing to download: the same
utterance produces the same intent, the same slots and the same reply on every run and on every
host.

### Final functionality

- an HTTP service that accepts one user turn and returns one assistant turn;
- a bundled corpus of English utterances, split into a `train` split read by the matcher and a
  `held-out` split read only by the accuracy test;
- intent matching by declared, deterministic token overlap;
- entity extraction by declared patterns and enumerations;
- slot filling across turns, with required slots per intent, a confirmation step and a reset;
- per-session memory, persisted in SQLite so a restart does not erase a conversation;
- a declared fallback path with a counter and escalation after three consecutive failures;
- one structured JSON log record per turn, enough to replay a conversation;
- a container that starts with one command and is verified headlessly.

### Non-goals

LLMs, embeddings, vector databases, speech, telephony, any external channel, multi-user auth, a web
UI beyond the HTTP endpoints below, deployment and hosting. The service also does not model the
back office behind an intent: completing an intent yields a declared template reply and a completed
record in the turn log, nothing more.

Dialogue quality is out of reach of a rules engine and is not scored; determinism, state modelling
and checkable behaviour are.

## 3. Architecture and module boundaries

```text

  nlu/
    normalise.py      lowercase, punctuation, stopwords, tokens

  migrations/001_init.sql

  corpus/train.jsonl  matcher input, one record per line
  corpus/heldout.jsonl accuracy input, never read by the matcher
  scripts/smoke_dialogue.py  scripted conversation against a live service

```

The boundaries are the seams the test suite uses:

- `nlu` are pure functions over strings and the corpus: given text and the loaded corpus they return
  plain dictionaries, never touching SQLite or Flask. Their tests import them directly, with no
  server and no database.
- `dialogue` is a pure transition function: given session state, the parsed turn and the corpus it
  returns the next state, the reply and the log fields. It writes nothing.
- `store` is the only module that opens SQLite; `api` is the only module that imports Flask.
- Dependencies point one way: `api → dialogue → nlu`, `dialogue → store`. `nlu` imports no local
  module.
- Everything is plain Python data (dictionaries and `@dataclass` records); no global mutable state
  beyond the SQLite connection owned by `store`.

## 4. Corpus and NLU contract

Three files, all committed. `schema.json` is the single source of truth for the intent and entity
declarations, so the corpus and the matcher cannot disagree.

### Intent declarations

| intent | required slots | notes |
|---|---|---|
| `greet` | — | single-turn |
| `book_table` | `day`, `time`, `party_size` | three-slot conversation |
| `cancel_booking` | `booking_id` | the slice intent |
| `check_order_status` | `order_id` | single-slot conversation |
| `change_address` | `order_id`, `city` | two-slot conversation |
| `goodbye` | — | single-turn |
| `reset` | — | dialogue control, accepted in every state |

### Entity declarations

| entity | kind | declaration |
|---|---|---|
| `booking_id` | pattern | `^BK-[0-9]{5}$` |
| `order_id` | pattern | `^[A-Z]{2}-[0-9]{4}$` |
| `time` | pattern | `^[0-9]{2}:[0-9]{2}$` with aliases (`noon` → `12:00`, `evening` → `19:00`) |
| `day` | enum | the seven weekday names plus the two literal tokens `today` and `tomorrow`, with short aliases (`fri` → `friday`) |
| `party_size` | enum | `1`–`8`, with word aliases (`two` → `2`, `a couple` → `2`) |
| `city` | enum | five declared cities, with aliases (`milano` → `milan`) |

`day` deliberately keeps `today` and `tomorrow` as literal tokens and never resolves them to a
calendar date: date arithmetic would import the clock and break reproducibility. The entity
declaration order in `schema.json` is significant — it is the scan order, and it is part of the
contract.

### File shapes

```json
{
  "version": 1,
  "thresholds": { "intent_accept": 0.5, "escalate_after_fallbacks": 3 },
  "stopwords": ["a", "an", "the", "my", "i", "to", "for", "of", "is", "it"],
  "intents": [
    {
      "name": "cancel_booking",
      "priority": 3,
      "required_slots": ["booking_id"],
      "slot_sources": { "booking_id": ["booking_id"] }
    }
  ],
  "entities": { "booking_id": { "kind": "pattern", "pattern": "^BK-[0-9]{5}$" } },
  "prompts": { "booking_id": "What is the booking reference?" },
  "confirm": { "affirm": ["yes", "yeah", "correct", "confirm"], "deny": ["no", "nope", "wrong"] },
  "replies": { "fallback": "Sorry, I did not understand that.", "confirm_reminder": "Please answer yes or no." },
  "confirm_templates": { "cancel_booking": "Cancel booking {booking_id}. Confirm?" },
  "effects": { "cancel_booking": "Booking {booking_id} is cancelled." }
}
```

`train.jsonl` and `heldout.jsonl` have one JSON record per line: `{"intent": "...", "text": "..."}`
and, for the held-out split, an additional `"expect_entities": {"booking_id": "BK-00417"}`. File
order is declaration order and is used by the tie-break, so the files are part of the interface.

Corpus minimums, asserted by a test rather than promised in prose: at least 8 train records per
intent and at least 48 in total; exactly 4 held-out records per intent and 24 in total; no held-out
text equal, after normalisation, to a train record.

`corpus.load_train(path)` accepts only the path of the train split and raises on any other path, so
the held-out file cannot reach the matcher through the loader. The accuracy test reads it directly.

### Matcher

Deterministic, declared, with no dependence on iteration order:

1. `normalise(text)`: lowercase; replace every character outside `[a-z0-9]` with a space; collapse
   runs of spaces; split; drop stopwords. The result is an ordered token list.
2. For each train record compute `|A ∩ B| / |A ∪ B|` over the token *sets* of the utterance and the
   record; an empty union scores 0.
3. An intent's score is the maximum over its own records; the winning record index is reported as
   `matched_example` so a decision can be traced to one line of the corpus.
4. The intent is accepted when the top score is at least `thresholds.intent_accept` (0.5); otherwise
   the turn has no intent and takes the fallback path.
5. Tie-break, fully ordered: higher score, then higher intent `priority`, then lower intent index in
   `schema.json`, then lower record index. No set is ever iterated to produce output.
6. `confidence` is the winning score rounded to three decimals; comparisons in tests use a tolerance
   of 0.001.

### Entities

Scan the case-normalised raw utterance once, in declaration order. A `pattern` entity matches at a
word boundary; an `enum` entity matches the longest declared value or alias. Values are reported in
canonical form. When one entity type could match twice, the earliest match position wins. All
distinct entity types found in an utterance are reported, regardless of the active intent.

## 5. Dialogue state machine

Four states, and one table that is the contract.

| from | event | to | effect |
|---|---|---|---|
| `idle` | intent accepted, no required slots | `idle` | reply from `effects`, transition `intent_completed` |
| `idle` | intent accepted, every required slot extracted | `confirming` | reply from `confirm_templates`, `confirm_requested` |
| `idle` | intent accepted, slots missing | `collecting` | ask the first missing slot in declared order, `slot_requested` |
| `idle` | no intent accepted | `idle` or `escalated` | fallback |
| `collecting` | answer fills the expected slot | `collecting` | ask the next missing slot, `slot_filled` |
| `collecting` | answer fills the last missing slot | `confirming` | confirmation prompt, `slot_filled` |
| `collecting` | intent accepted, different intent | `collecting` | new active intent, ask its first missing slot, `intent_switched` |
| `collecting` | nothing usable | `collecting` or `escalated` | fallback |
| `confirming` | utterance in `confirm.affirm` | `idle` | `effects` reply, slots and active intent cleared, `intent_completed` |
| `confirming` | utterance in `confirm.deny` | `collecting` | pending request discarded, slots cleared, ask the first slot again, `confirmation_declined` |
| `confirming` | anything else | `confirming` | fallback and repeat `replies.confirm_reminder`, `fallback` |
| `escalated` | anything else | `escalated` | repeat the escalation reply with the same ticket, `noop` |
| any non-`escalated` state | `reset` intent | `idle` | slots, active intent and fallback counter cleared, turns kept, `reset` |

Slot precedence inside `collecting`, in this order:

1. extract entities from the utterance;
2. an accepted intent different from the active one wins: the active intent is abandoned and its
   slots are dropped, the new intent's own slots are filled from the extracted entities;
3. otherwise, if the expected slot's entity type is present, its canonical value fills that slot;
4. otherwise the turn is a fallback;
5. a value for an already-filled slot overwrites it inside `collecting` and is logged as
   `slot_overwritten`; inside `confirming` slots are never overwritten.

Confirmation is a closed vocabulary, matched exactly after normalisation to one or two tokens; the
matcher is not consulted in `confirming`. This is the decision that keeps the confirmation step
from drifting as the corpus grows.

The transition identifiers form a closed set, because the log and the tests both read them:
`slot_requested`, `slot_filled`, `slot_overwritten`, `intent_switched`, `confirm_requested`,
`intent_completed`, `confirmation_declined`, `fallback`, `escalated`, `reset`, `noop`.

Every template in `prompts`, `confirm_templates`, `effects` and `replies` lives in `schema.json`
and is rendered at reply time; `replies.py` fails at startup when a template references a
placeholder that is not a declared slot of the intent or a global key of the render context.

Escalation is specified in § 7; it is the only place where a session can leave the "keep trying"
loop other than completing an intent.

## 6. Persistence

One SQLite file at `/data/rulechat.db`, on the named volume `rulechat-data`, created and migrated at
process start before the first request is served.

```sql
CREATE TABLE schema_version (
  version    INTEGER PRIMARY KEY,
  applied_at TEXT NOT NULL
);

CREATE TABLE sessions (
  id               TEXT PRIMARY KEY,
  state            TEXT NOT NULL CHECK (state IN ('idle','collecting','confirming','escalated')),
  active_intent    TEXT,
  fallback_count   INTEGER NOT NULL DEFAULT 0,
  escalation_count INTEGER NOT NULL DEFAULT 0,
  next_turn_index  INTEGER NOT NULL DEFAULT 0,
  created_at       TEXT NOT NULL,
  updated_at       TEXT NOT NULL
);

CREATE TABLE slots (
  session_id TEXT NOT NULL REFERENCES sessions(id) ON DELETE CASCADE,
  name       TEXT NOT NULL,
  value      TEXT NOT NULL,
  PRIMARY KEY (session_id, name)
);

CREATE TABLE turns (
  session_id     TEXT NOT NULL REFERENCES sessions(id) ON DELETE CASCADE,
  turn_index     INTEGER NOT NULL,
  text           TEXT NOT NULL,
  normalised     TEXT NOT NULL,
  intent         TEXT,
  confidence     REAL,
  matched_example INTEGER,
  slots_json     TEXT NOT NULL,
  transition     TEXT NOT NULL,
  state_after    TEXT NOT NULL,
  created_at     TEXT NOT NULL,
  PRIMARY KEY (session_id, turn_index)
);

CREATE INDEX turns_by_session ON turns (session_id, turn_index);
```

Rules:

- one migration per file in `migrations/`, applied in filename order, each inside its own
  transaction and recorded in `schema_version`; an applied migration is never edited, and a gap
  between the files on disk and `schema_version` stops the process with a message instead of a
  silent schema drift;
- a turn is one transaction: the session row, the slot delta and the turn row commit together, so a
  failed turn leaves no partial state;
- `turn_index` starts at 0 and is contiguous per session; `next_turn_index` on the session row is the
  allocator;
- `created_at` is recorded and is excluded from every deterministic comparison; nothing else in the
  schema depends on the clock;
- two sessions never share rows, and a session id never appears in another session's turns;
- the conversation survives `docker compose restart rulechat`: state, slots and turns come back, and
  the next turn continues with the next `turn_index`.

## 7. Fallback and escalation

- A turn with no accepted intent and no usable slot answer increments `fallback_count`; the reply is
  `replies.fallback`.
- Any turn that fills or completes something resets `fallback_count` to 0.
- At `thresholds.escalate_after_fallbacks` (3) consecutive fallbacks the session enters `escalated`
  and the reply is `replies.escalation` with ticket `ticket_id`.
- `ticket_id = "ESC-" + sha256(session_id + "|" + str(escalation_count))[:8]`: no randomness and no
  clock, so two runs of the same conversation produce the same ticket sequence.
  `escalation_count` increments when the escalation happens and is persisted, so neither a restart
  nor a reset reissues a ticket.
- In `escalated` the counter is frozen: further unparseable turns repeat the escalation reply with
  the same ticket and change nothing else. Only the `reset` intent leaves the state; it clears
  `fallback_count` and `active_intent`, keeps the turn history, and leaves `escalation_count` alone
  so a later escalation in the same session gets a new ticket.

## 8. HTTP API

Four endpoints. Requests and responses are JSON; errors are JSON too, never HTML.

| method | path | purpose |
|---|---|---|
| `POST` | `/chat` | one user turn in, one assistant turn out |
| `GET` | `/session/<id>` | current state, slots and the ordered turns (replay) |
| `POST` | `/session/<id>/reset` | clear slots, active intent and fallback counter, keep turns |
| `GET` | `/healthz` | `{"status":"ok","schema_version":1}` once migrations are applied |

`POST /chat` request:

```json
{"session_id": "slice-0001", "text": "I need to cancel my booking"}
```

`session_id` is optional and must match `^[A-Za-z0-9_-]{1,64}$` when supplied; omitting it creates a
session and the id is echoed back, which is what the HTTP client uses on the first turn. A supplied
id that does not exist is `404`, never an implicit create — the scripted checks rely on that, since
it is how they prove a session is really persisted.

`POST /chat` response:

```json
{
  "session_id": "slice-0001",
  "turn_index": 0,
  "reply": "What is the booking reference?",
  "intent": "cancel_booking",
  "confidence": 1.0,
  "matched_example": 2,
  "slots": {},
  "missing_slots": ["booking_id"],
  "state": "collecting",
  "transition": "slot_requested",
  "fallback_count": 0,
  "escalation": null
}
```

`escalation` is either `null` or `{"ticket": "ESC-1a2b3c4d", "count": 1}`.

Error bodies, all with the same shape `{"error": "<code>"}`: `400 empty_text` for a blank or
whitespace-only text, `400 malformed_json` for a body that is not a JSON object, `400 bad_session_id`
for an id outside the pattern, `404 unknown_session`, `413 body_too_large` above 4 KiB, and
`500 internal` for an unexpected exception — which is logged once and leaves the process running.
Unknown request fields are ignored so a client may send extra metadata.

## 9. Structured logging

One JSON object per turn on stdout, and nothing else on stdout; diagnostics go to stderr.

```json
{"event":"turn","session_id":"slice-0001","turn_index":1,"text_sha256":"…","intent":null,
 "confidence":null,"matched_example":null,"slots_after":{"booking_id":"BK-00417"},
 "state":"confirming","transition":"slot_filled","fallback_count":0,"escalation_ticket":null}
```

The key set is fixed and every key is always present. The raw utterance never appears: the record
carries `text_sha256`, the sha256 of the raw text, so a conversation can be replayed against a known
script without logging user-like content. The record carries no timestamp — the clock lives in
`turns.created_at` — so two runs of the same script produce identical log lines, and a test asserts
that by replaying the scripted conversation twice and diffing the captured stdout.

Replay requirement: reading the turn records in `turn_index` order from the database must reproduce
the same `(intent, transition, state, slots_after)` sequence as the captured log lines. A test
cross-checks the two sources, which is what makes the log evidence rather than decoration. The raw
utterance is stored in `turns.text`, because replay needs it; it never reaches the log.

- held-out accuracy meets the declared binary threshold: **at most one of the 24 held-out utterances
  may be misclassified**, where a record counts as correct only when both the intent and its
  declared `expect_entities` values match;
- the accuracy test reports the misclassified records by corpus line number;
- a test asserts the matcher module's corpus allowlist contains only the train split, so the
  threshold cannot be met by reading the held-out split.

The threshold is binary on purpose: a percentage invites tuning the corpus instead of the matcher,
while "all but at most one" either holds or does not.

**Verify:**


## 11. Test suite requirements

Tests import `nlu` and `dialogue` as pure functions and reach `store` through a temporary SQLite
file; only the API and persistence tests start the Flask app, and only inside the container through
`docker compose exec`.

Required coverage:

- **normalisation**: case, punctuation, stopwords, empty input, unicode-free input, tokens that
  differ only by punctuation;
- **matching**: above threshold, below threshold, exact tie at every tie-break level, no train record
  in common, one-word utterances, and a corpus record that shares every token;
- **entities**: each declaration, each alias, the earliest-position rule, a pattern that almost
  matches, and a value that would fit two types;
- **transitions**: every row of the § 5 table, the confirmation vocabulary boundary, deny, intent
  switch, reset from each state;
- **persistence**: migration idempotence, contiguous turn indices, two interleaved sessions, a
  rejected request writing nothing, a restart continuing the conversation;
- **fallback and escalation**: the threshold, the counter reset, the frozen escalation state, ticket
  determinism and uniqueness per escalation;
- **slice**: the three-turn transcript of § 10 against the live HTTP API;
- **determinism**: the same scripted conversation twice, diffed on the log records and on the
  response bodies, and the corpus metadata compared byte for byte;
- **isolation**: `socket.socket.connect` is patched in `tests/conftest.py` to raise for any address
  outside `127.0.0.1`/`::1`, so a test that accidentally reaches the network fails loudly instead of
  depending on the sandbox.

## 13. Operating instructions for the development agent

- Work one milestone at a time and keep the service runnable after each one; M0 is the only milestone
  whose omission blocks everything else.
- Write the tests of a milestone before its implementation, and keep them pure where § 3 says the
  seam is pure.
- Keep `schema.json` the only place where an intent, a slot, an entity, a threshold or a reply
  template is declared. When behaviour changes, the declaration changes first.
- Never read `corpus/heldout.jsonl` outside the accuracy test, and never tune the matcher against it.
- Keep the transition identifiers and the log keys exactly as declared: the tests, the log replay and
  the milestone details all read them.
- Keep the process single-threaded and the store the only writer; a background task or a second
  process invents a problem this benchmark does not need.
- When a rule-based answer is wrong, fix the rule or the corpus declaration; do not add a special
  case in `api.py`.
- Report, before declaring a milestone done: changed files, commands run, test results, the slice
  transcript and residual risks.

## Verify

`./verify.sh` is the single verification entry point: non-interactive, timeout 600 s, exit 0 if and
only if every milestone passed. Sequence:

1. `docker compose up --wait --build` — build with hash-pinned installs, migrations applied on the
   empty volume, `/healthz` healthy. Failure here fails `M0` and stops the remaining steps that need
   the service while still writing `verify.json`.
2. `docker compose exec -T rulechat pytest -q` — the whole suite, including the case tables, the
   held-out accuracy gate and the isolation guard.
3. `docker compose exec -T rulechat python -m rulechat.scripts.smoke_dialogue --base-url
   http://127.0.0.1:8000 --session slice-0001` — the three-turn slice transcript over HTTP,
   compared against the declared expectations of § 10.
4. The same script with `--session slice-0002`, then `docker compose restart rulechat`, then
   `GET /session/slice-0002` compared to the state recorded before the restart, then one further
   turn that must continue at the next `turn_index`; the captured stdout logs of steps 3 and 4 are
   diffed to prove replay determinism.
5. `emit_verify.py` maps collected evidence onto `M0`–`M6` and writes `verify.json` in the
   project root next to `verify.sh`: `schema: 1`, `benchmark: "rulechat"`, every milestone id
   exactly once with `pass` and a `detail` naming the evidence, plus `notes` with the wall clock of
   the run.
6. `docker compose down -v` — always, through a trap, also on failure, interrupt or timeout.

Milestone evidence, so a `pass` is never a judgement call:

| id | passes when |
|---|---|
| `M0` | Compose healthy, `/healthz` 200, slice transcript matched on 3 turns |
| `M1` | the NLU tests and the corpus guard passed |
| `M2` | the FSM and reply tests passed |
| `M3` | the store tests passed and step 4's restart continued the conversation |
| `M4` | the fallback and escalation tests passed |
| `M5` | the case tables, the held-out accuracy gate and the determinism tests passed |
| `M6` | steps 1–5 all ran and `verify.json` was written with the seven ids |

Determinism is asserted, not assumed: two runs of the same script against fresh sessions must
produce identical response bodies and identical log records, with `created_at` the only excluded
field.
