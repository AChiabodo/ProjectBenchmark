# Plan — MiniLang: a small language, interpreter included

## 1. Goal and scope

Implement a tree-walking interpreter for MiniLang, a language this plan declares in full. The
language is small on purpose and closed: every production, every precedence level and every runtime
error is written below, so "correct" is a property of the program text and not a matter of taste.
There is no graphics, no network, no standard library beyond `print`, and nothing to download.

### Final functionality

- a lexer, a recursive-descent parser producing an AST, and a tree-walking evaluator;
- integer and floating arithmetic over one numeric type, with declared precedence and associativity;
- variables with block scope, `let` and assignment, `if`/`else`, `while`;
- function declaration, parameters, `return`, recursion and mutual recursion;
- `print` with declared formatting, and no other observable effect;
- lexical, syntax and runtime diagnostics carrying kind, message, line and column;
- a REPL for interactive use and a file mode whose exit code reports success or failure;
- a table-driven case suite of input/expected-output and input/expected-diagnostic pairs;
- `./verify.sh` writing `verify.json` with every milestone id of `meta.json`.

### Non-goals

`&&`, `||`, unary `+`, compound assignment, `++`, arrays, maps, records, closures, nested functions,
types beyond numbers, string values (the one exception is the string literal argument of `print`),
comments in block form, exponent literals, parse recovery and error cascades, a bytecode compiler, a
JIT, an optimiser, a formatter, a linter, a debugger, a package system, REPL history, syntax
highlighting, any GUI, notebook or web playground.

The difficulty is correctness across a formal grammar — lexical analysis, precedence, scope and
diagnostics — not the volume of features. A larger language scores nothing extra; a smaller one that
mis-parses `1+2*3` scores nothing at all.

## 2. Locked technical decisions

```text
Language:   Rust, edition 2021, one crate, one binary named minilang
Crates:     none; std only, so the build touches no registry and no source archive
Pipeline:   lexer -> parser -> AST -> tree-walking evaluator; no bytecode, no JIT
Values:     one numeric type (IEEE-754 double); no boolean type; a string exists
            only as the literal operand of print
Errors:     kind + message + line + column; the first error aborts, no recovery
Tests:      cargo test, table-driven case files, no network, no sleeps
Interfaces: REPL on stdin, file mode on one path argument
```

Milestones M0–M2 build a calculator over a declared grammar before any stretch content exists;
recursion is the only place where the evaluator can run away, so the call depth limit of § 4.8 is
part of the language, not of the harness.

### Pinned dependencies and deliverables

| item | pin | where |
|---|---|---|
| Rust toolchain | any stable with `edition = "2021"` support | `Cargo.toml`, `rust-toolchain.toml` optional |
| crates | none: `[dependencies]` is empty and stays empty | `Cargo.toml` |
| `Cargo.lock` | committed, and a deliverable of this project, not an artefact | repository root |

`Cargo.lock` is committed on purpose. With zero dependencies it is short, and it is what makes

`--offline` proves the build needs no network. Both flags appear in `verify.sh` and in every example
command below; a project whose build needs the registry fails `M0`.

### Commands — exactly one of each

```bash

./verify.sh                        # the single verification command
```

`cargo run --release --` with no operand starts the REPL; with one operand it runs that file. One
command, one optional operand, two modes. Building by hand, or `cargo test` invoked directly, is a
development convenience and never the Definition of Done.

```text

  src/value.rs          the numeric value and its formatting rule

  src/repl.rs           prompt, statement accumulation, per-line recovery

  tests/fixtures/slice/ the slice program and its two error programs
  tests/case_runner.rs  the harness that executes case tables
  verify.sh
```

The boundaries are the seams the suite uses:

- `lexer`, `parser` and `eval` are pure functions over owned data: `&str -> Vec<Token>`,
  `Vec<Token> -> Result<Program, Diagnostic>`, `&Program -> Result<Outcome, Diagnostic>`. Only
  `main.rs` and `repl.rs` write to stdout, stderr or the filesystem.
- `diagnostic.rs` is the only place that formats a `kind error at line:col: message` line, so the
  format of § 5 cannot drift between the three error sources.
- `print` output is captured as a string by the evaluator and emitted by the caller, so tests compare
  output as data and `main.rs` alone decides where the bytes go.
- No global mutable state; the global scope belongs to one `Interpreter` value.

## 4. The language

### 4.1 Lexical structure

The lexer takes the longest token that matches at the current position.

| token | form | notes |
|---|---|---|
| integer literal | `[0-9]+` | leading zeros are legal and value is decimal: `007` is 7 |
| float literal | `[0-9]+ "." [0-9]+` | `.5` and `5.` are lexical errors, and there is no exponent form |
| string literal | `"` … `"` | escapes `\"`, `\\`, `\n` only; any other escape is a lexical error |
| identifier | `[A-Za-z_][A-Za-z0-9_]*` | keywords are reserved and cannot be identifiers |
| keyword | `let if else while fn return print` | lowercase only |
| operators | `+ - * / % ! < <= > >= == != =` | `<= >= == !=` are one token each |
| punctuation | `( ) { } , ;` | the single statement terminator is `;` |
| comment | `//` to end of line | no block comment form |
| whitespace | space, tab, CR, LF | LF advances the line counter, CR does not |

Source is ASCII. A byte outside the ASCII range is a lexical error, as is any character that begins
no token of this table. Positions are 1-based: line 1 is the first line, column 1 is the first
character of a line, and a token's position is the position of its first character.

### 4.2 Grammar

```text
program          = { statement } EOF ;
statement        = let_decl | assignment | if_stmt | while_stmt | fn_decl
                 | return_stmt | print_stmt | block ;
let_decl         = "let" identifier "=" expression ";" ;
assignment       = identifier "=" expression ";" ;
if_stmt          = "if" "(" expression ")" block [ "else" block ] ;
while_stmt       = "while" "(" expression ")" block ;
fn_decl          = "fn" identifier "(" [ identifier { "," identifier } ] ")" block ;
return_stmt      = "return" expression ";" ;
print_stmt       = "print" ( expression | string ) ";" ;
block            = "{" { statement } "}" ;
expression       = equality ;
equality         = comparison { ( "==" | "!=" ) comparison } ;
comparison       = additive { ( "<" | "<=" | ">" | ">=" ) additive } ;
additive         = multiplicative { ( "+" | "-" ) multiplicative } ;
multiplicative   = unary { ( "*" | "/" | "%" ) unary } ;
unary            = ( "-" | "!" ) unary | primary ;
primary          = integer | float | identifier | call | "(" expression ")" ;
call             = identifier "(" [ expression { "," expression } ] ")" ;
```

Rules that belong to the grammar and produce syntax errors when broken:

- every statement except a block is terminated by `;`; a block is terminated by its `}`;
- `else` is followed by a block, so `else if` is a syntax error; write `else { if … }`;
- `fn` appears only at the top level of a program; a `fn` inside a block is a syntax error;
- a string literal is legal only directly after `print`; anywhere else it is a syntax error;
- an identifier followed by `(` is a call, and there is no other postfix form;
- there are no expression statements: `1+2;` on its own is a syntax error, `print 1+2;` is not.

A syntax error is reported at the first token that cannot continue the parse, which is often the
token *after* the incomplete construct: `print 1+;` fails at the `;`, not at the `+`.

### 4.3 Values, numbers and printing

There is exactly one value type: an IEEE-754 double. Integer literals and float literals produce the
same type, so `1` and `1.0` are the same value and arithmetic never needs a conversion rule.

- `/` is floating division: `print 1/2;` prints `0.5`, and there is no integer division operator.
- `%` is the truncated remainder, so the result carries the sign of the dividend: `-7 % 3` is `-1`.
- Division and remainder by zero are runtime errors, never infinity or NaN.
- A result that is not finite is a runtime error, so `inf` and `nan` can neither be produced nor
  printed; very large finite values still format under the rule below.
- `print` writes its operand followed by a single newline, and is the only observable effect.

Formatting of a number is fixed, because the case tables compare bytes:

1. if the value is finite, equal to its own truncation, and of magnitude at most 2^53, print it as a
   decimal integer with no fractional part and no exponent: `3`, `-7`, `0`;
2. negative zero prints as `0`, under rule 1;
3. otherwise print the shortest decimal representation that reads back as the same double:
   `0.5`, `1.25`, `0.1`, `-2.5`.

A string literal operand of `print` is written verbatim after its escapes are resolved, then the same
newline. There is no concatenation, because a string is not a value.

### 4.4 Operator precedence and associativity

Tightest first; parentheses override and `()` never changes a value.

| level | operators | form | associativity | result |
|:-----:|-----------|------|---------------|--------|
| 1 | `-` `!` | prefix | right | negation; `!` maps 0 to 1 and any non-zero to 0 |
| 2 | `*` `/` `%` | infix | left | arithmetic of § 4.3 |
| 3 | `+` `-` | infix | left | arithmetic of § 4.3 |
| 4 | `<` `<=` `>` `>=` | infix | left | 1 when true, 0 when false |
| 5 | `==` `!=` | infix | left | 1 when true, 0 when false |

Consequences, which the suite asserts: `print 1+2*3;` prints `7`, `print (1+2)*3;` prints `9`,
`print 2-3-4;` prints `-5`, `print -2*3;` prints `-6`, `print 1<2==1;` prints `1`.

### 4.5 Truthiness

There is no boolean type. A condition is true if and only if its value is not zero; `0`, `-0`, and
`0.0` are false, every other number is true. Comparisons and `!` yield the numbers 1 and 0, so they
compose with the arithmetic rules instead of needing a separate type.

### 4.6 Statements and execution

- A program executes its statements in order; output is the concatenation of every `print`, each
  followed by one newline.
- `if` executes its then-block when the condition is true and its optional else-block otherwise.
- `while` evaluates the condition before each iteration and executes the block while it is true; the
  case tables contain no non-terminating program, and termination is not something the interpreter
  enforces.
- `return` inside a function body ends that body; `return` outside a function body is a runtime
  error.
- Execution stops at the first error of any kind. Output already written stays written, and
  `verify.sh` compares exactly that prefix.

### 4.7 Scopes, declaration and assignment

- One global scope holds everything a program declares at the top level. Every block and every
  function body introduces a scope; a `while` body gets a fresh scope per iteration, so a `let`
  inside it cannot leak into the next iteration.
- `let NAME = expression;` introduces a binding in the current scope. Declaring the same name twice
  in the same scope is a runtime error; shadowing a binding of an outer scope is allowed and ends
  with that scope.
- `NAME = expression;` assigns to the nearest enclosing binding that declares the name. Assigning a
  name that no scope declares is a runtime error, not an implicit declaration.
- Scoping is lexical. A block sees its own bindings and those of the scopes around it, and never a
  caller's.

### 4.8 Functions

- `fn` declares a named function at the top level. All declarations of a program are collected
  before execution begins, so a call may appear before its declaration and mutual recursion works.
- Parameters are bindings in a fresh call scope whose parent is the global scope, never the caller's
  scope: functions read their parameters, their own locals and globals, nothing else.
- The argument count must equal the parameter count; a mismatch, or a call to a name that is not a
  declared function, is a runtime error.
- A body that ends without executing `return` yields 0.
- Function names are not values. Using a function name in an expression is a runtime error, matching
  the "undefined variable" case, because name resolution looks at bindings only.
- Call nesting is limited to 1000 frames; exceeding it is a runtime error, which is what keeps
  `fn f(n) { return f(n + 1); } print f(0);` a diagnosis instead of a stack overflow.
- No closures, no nested function declarations, no default parameters, no variadic calls.

### 4.9 The runtime errors of the language

A runtime error carries the position of the operator or the name token that failed.

| condition | message shape |
|---|---|
| `/` or `%` whose right operand is 0 | `division by zero` |
| a result that is not finite | `numeric overflow` |
| assignment to a name no scope declares | `undefined variable 'x'` |
| a second `let` of one name in one scope | `redeclaration of 'x'` |
| a function name used as a value | `undefined variable 'f'` |
| a call to a name that is not a declared function | `unknown function 'g'` |
| an argument count that does not match the parameters | `'f' expects 2 arguments, 3 given` |
| more than 1000 nested calls | `call depth limit exceeded` |
| `return` outside a function body | `return outside a function` |

The message text is the implementation's, chosen once and then snapshotted. The kind, the line and
the column are fixed by this plan and are what the suite scores.

### 4.10 Locked example programs

These pairs are part of the specification: if an implementation disagrees with one of them, the
implementation is wrong.

| program | stdout |
|---|---|
| `print 1+2*3;` | `7` |
| `print 1/2;` | `0.5` |
| `print -7 % 3;` | `-1` |
| `let x = 2; let y = 3; print x*y;` | `6` |
| `let i = 0; while (i < 3) { print i; i = i + 1; }` | `0`, `1`, `2` |
| `if (1) { print 10; } else { print 20; }` | `10` |
| `if (0) { print 10; } else { print 20; }` | `20` |
| `let n = 5; if (n > 3) { let n = 1; print n; } print n;` | `1`, `5` |
| `fn add(a, b) { return a + b; } print add(2, 5);` | `7` |
| `fn fac(n) { if (n < 2) { return 1; } return n * fac(n - 1); } print fac(5);` | `120` |
| `fn even(n) { if (n == 0) { return 1; } return odd(n - 1); } fn odd(n) { if (n == 0) { return 0; } return even(n - 1); } print even(6);` | `1` |
| `fn zero() { let x = 1; } print zero();` | `0` |
| `print "total:"; print 7/2;` | `total:`, `3.5` |

## 5. Diagnostics

Three kinds exist, and the kind word is part of the output:

| kind | source | example |
|---|---|---|
| `lexical` | the lexer cannot begin a token | `print 1 $ 2;` |
| `syntax` | the parser cannot continue with the token it sees | `print 1+;` |
| `runtime` | the evaluator hits a condition of § 4.9 | `print 1/0;` |

One diagnostic is one line on stderr, in exactly this format:

```text
<kind> error at <line>:<col>: <message>
```

`kind` is one of `lexical`, `syntax`, `runtime`; `line` and `col` are 1-based decimal integers with no
padding; `message` is non-empty, single-line and starts with a non-space character. Nothing else is
written to stderr on a failing run, and nothing at all on a succeeding one. The three programs above
produce, byte for byte:

```text
lexical error at 1:9: unexpected character '$'
syntax error at 1:10: expected an expression
runtime error at 1:8: division by zero
```

The format is fixed here so that a case table can compare a diagnostic as a snapshot and so that a
harness can parse the kind and the position out of it. Only the first error is reported: recovery,
cascades and warnings are out of scope, and a program with two errors reports the earlier one.

## 6. Interfaces — REPL and file mode

### File mode

`minilang FILE` reads that file, executes it, and exits:

| exit | condition |
|---:|---|
| 0 | the program ran to completion |
| 1 | a lexical, syntax or runtime error, whose one diagnostic line is on stderr |
| 2 | a usage error: no such file, unreadable file, or more than one operand |

`print` output goes to stdout and nothing else does. A program that prints and then fails keeps its
printed lines on stdout, prints one diagnostic on stderr and exits 1.

### REPL

`minilang` with no operand reads stdin. It accumulates one statement at a time: a statement is
complete when a `;` closes it at brace depth 0, or when a closing `}` closes a block at depth 0, with
comments ignored. The two prompts go to stderr and are fixed:

| prompt | when | bytes |
|---|---|---|
| statement prompt | before reading the first line of each statement | `> ` |
| continuation prompt | before reading each further line of an unfinished statement | `.. ` |

REPL rules:

- bindings and functions survive from one line to the next, and share the global scope of the mode,
  so the REPL accumulates a program instead of restarting one;
- a diagnostic is printed in the format of § 5 and the REPL continues with the next statement;
- positions in a REPL diagnostic are relative to the statement being parsed, whose first line is
  line 1, so a continuation line is line 2 and so on;
- a blank line at the start of a statement is ignored, and the statement prompt is written again
  before the next line;
- nothing is echoed for a statement that does not print;
- input `:quit` alone on a line exits 0; end of input also exits 0;
- the prompts make REPL transcripts deterministic: stdin is piped in the suite, so nothing else on
  stderr varies.

Two transcripts, exact bytes, are the contract:

| input | stdout | stderr | exit |
|---|---|---|---|
| `let x = 1 +` then `2;` then `print x;` | `3` | `> .. > > ` | 0 |
| `print 1+;` | — | `> syntax error at 1:10: expected an expression` then `> ` | 0 |

## 8. Case tables

One text file per feature under `tests/cases/`, committed, human-readable and diffable. A file-mode
case is a header line and four blocks in this order:

```text
=== integer arithmetic
--- program
print 1+2*3;
--- stdout
7
--- stderr
--- exit
0
```

A REPL case is a header line prefixed `repl: ` and its blocks start with `--- input`:

```text
=== repl: error then continue
--- input
print 1+;
print 6*7;
--- stdout
42
--- stderr
> syntax error at 1:10: expected an expression
> >
--- exit
0
```

Rules for both forms:

- a case header is `=== ` followed by a unique name; the blocks follow in the declared order;
- a block body is every line between its header and the next header, verbatim; an empty block is an
  empty body;
- `--- exit` holds one line: the expected exit status;
- a file-mode case writes the program to a temporary file and runs `minilang FILE`; a REPL case pipes
  the input and runs `minilang` with no operand;
- comparison is byte-exact on stdout and stderr, so a diagnostic is snapshotted whole;
- the temporary file is created under the OS temp directory and removed by the runner.

Required files and minimums: `arith.txt` 10, `values.txt` 8, `variables.txt` 8, `control.txt` 8,
`functions.txt` 10, `print.txt` 6, `diagnostics.txt` 12, `repl.txt` 6. Together they cover every
precedence level, every formatting rule, every runtime error row, the two interface modes and both
error kinds of the slice.

## 10. Operating instructions for the development agent

- Work one milestone at a time and keep the build green after each one; M0 is the only milestone
  whose omission blocks everything else.
- Write the case for a rule before implementing the rule, and change the language only by changing
  this plan's declaration first: the plan is the specification, the implementation follows it.
- Keep one spelling per concept. `kind`, `line`, `col`, `message` are the four fields of a diagnostic
  everywhere, and `Interpreter`, `Environment`, `Value` are the three nouns of the runtime.
- Never let two modules format a diagnostic; `diagnostic.rs` is the only formatter, which is what
  makes the § 5 format survive all three error sources.
- Keep the pipeline honest: no evaluation during parsing, no lexing during evaluation, no special
  case in the parser for a program the evaluator should reject.
- Prefer a smaller language that is fully declared over an extra feature that the plan does not
  mention; `&&`, `||`, arrays and closures are non-goals even when they look like five minutes of
  work.
- Report, before declaring a milestone done: changed files, commands run, test counts, the three
  slice fixtures and their exit codes, and residual risks.

## Verify

`./verify.sh` is the single verification entry point: non-interactive, timeout 600 s, exit 0 if and
only if every milestone passed. Sequence:

1. `cargo build --release --locked --offline` — offline build with the committed lock file; a build
   that needs the registry fails here and fails `M0`.
2. `cargo test --release --locked --offline` — unit tests plus the whole case suite of § 8, which
   drives the release binary for every case, diagnostic snapshots and CLI cases included.
3. The three slice fixtures run through the release binary, their stdout, stderr and exit codes
   compared byte for byte against § 5 and M0.
4. The REPL transcripts of § 6 are piped through the release binary and compared byte for byte,
   prompts included.
5. The evidence is mapped onto `M0`–`M6` and written to `verify.json` in the project root next to
   `verify.sh`: `schema: 1`, `benchmark: "minilang"`, every milestone id exactly once with `pass` and
   a `detail` naming the evidence, plus `notes` with the wall clock of the run.

Milestone evidence, so a `pass` is never a judgement call:

| id | passes when |
|---|---|
| `M0` | the build is offline and `--locked`, and all three slice fixtures match bytes and exit codes |
| `M1` | the lexer and parser tests passed, including every declared syntax error and its position |
| `M2` | the evaluator tests passed, including the four arithmetic runtime errors |
| `M3` | the function tests passed, including hoisting, arity, the 1000-frame limit and scope isolation |
| `M4` | the two REPL transcripts matched and the three exit codes were observed |
| `M5` | the case files exist above their minimums and every case passed |
| `M6` | steps 1–5 all ran and `verify.json` was written with the seven ids |

Failure is reported, never hidden: a failing step records `pass: false` with the failing case name for
its milestone and the remaining steps still run, so one broken feature does not erase the evidence for
the others.
