# Plan — Connect4-Minimax: deterministic search engine

## 1. Goal and scope

Build a Connect Four engine whose **search** is the thing being measured. The rules are small and
standard, the algorithm is textbook, and both are easy to get subtly wrong: a win detector that
misses the anti-diagonal, an alpha-beta that prunes with the wrong window, an evaluation that is
computed from the wrong perspective. The Plan therefore pins the parts that are objectively
checkable — board geometry, move notation, terminal detection, evaluation weights, search scores,
node counting, perft values — and leaves the data structures free.

Nothing here is downloaded and nothing is learned: the same position, the same depth and the same
options produce the same move, the same score and the same node count on every run and every host.
There is no window, no graphics and no network.

### Final functionality

- a 7 × 6 board with declared gravity, move legality and terminal detection, including draws;
- negamax with alpha-beta over a declared centre-first move order, at a configurable depth;
- a window evaluation with declared weights, from the perspective of the side to move;
- an optional transposition table that may change node counts but never the chosen move;
- a millisecond budget through iterative deepening, so "strong" means strong within a stated time;
- an interactive text CLI to play against the engine, and a scripted mode that consumes a move
  sequence and emits one JSON record with the chosen move, score, depth and node count;
- a perft harness and a self-play harness over fixed positions, with committed reference values;
- a deterministic timing workload with a declared threshold;
- a test suite whose oracle is an independent full-width minimax, so pruning is demonstrated
  rather than claimed.

### Non-goals

GUI, web frontend, sound, animation, opening books, endgame databases, neural or learned
evaluation, tournaments, strength comparison against external engines, packaging, deployment.
The search is **single-threaded**: parallelism would make node counts and the timing check
machine-dependent, which is the opposite of what this benchmark measures.

The boundaries are the seams the test suite uses:

- `Connect4.Core` is a pure library: given a position, options and (in budgeted mode) a clock

  a human, and never depends on `Console`.

  decision it makes is delegated to `Connect4.Core`, so the CLI tests exercise the same code the
  unit tests do.
- Dependencies point one way: `Cli → Core`, `Tests → Core`. `Core` references nothing.

## 4. Rules and board contract

Seven columns, six rows. Columns are numbered **1 to 7** left to right; that number is the move
notation everywhere — CLI input, move sequences, JSON fields. Rows are counted from the bottom,
0 to 5; nothing in the output depends on that numbering, it exists so the Plan can name a cell
when it talks about diagonals.

- **Players**: `X` moves first, `O` moves second. `X` moves when both counts are equal, `O` moves
  when `X` has one more disc. Cell glyphs are `X`, `O` and `.` for empty.
- **Gravity**: a disc played in column *c* lands on the lowest empty row of *c*. There is no other
  way to place a disc.
- **Legality**: a move is legal when the column number is 1–7 and the column holds fewer than six
  discs. A full column is not a legal move, and a rejected move changes nothing.
- **Terminal detection**: the game is won by the player who, by their last move, first owns four
  discs in a line — horizontal, vertical, or either diagonal, on contiguous cells. A line broken by
  an empty cell or by an opponent disc is not a win. The board is full with no win: draw. Once
  terminal, no further move is legal.
- **Move sequences** are digit strings, one digit per ply, e.g. `4433`. Replaying a sequence is the
  only way fixtures build a position, so every fixture is reachable by construction and the replay
  itself checks legality: an illegal digit, or a digit after the game ended, rejects the whole
  sequence.

A position is **consistent** when all three hold: every column's discs occupy the bottom cells
contiguously, the two disc counts differ by at most one, and the side to move matches the counts.
`Board` exposes a validation call that reports which of the three failed, and both the fixture
loader and the CLI's scripted mode use it. An inconsistent position is a bug in the caller, not a
position the engine guesses about: it is rejected with exit code 3 and the reason.

`GameResult` is one of `ongoing`, `win:X`, `win:O`, `draw` — those four strings appear in the CLI
output, in the JSON records and in the fixtures, so nothing re-spells them.

## 5. Search contract

Negamax with alpha-beta, single-threaded, deterministic.

```text
WIN = 1_000_000
score(terminal win by the side to move at ply p) =  WIN - p     (p = plies from the root, 1-based)
score(terminal loss)                             = -WIN + p
score(draw)                                      =  0
score(non-terminal leaf)                         =  eval(position, side to move)   (§ 6)
```

A win that arrives sooner scores higher and a loss that arrives later scores lower, so the search
prefers the shortest win and the longest resistance. `WIN` is three orders of magnitude above the
evaluation bound of § 6, so a heuristic advantage can never outrank a forced result.

- **Move order**: `[4, 3, 5, 2, 6, 1, 7]`, centre first, declared once in `MoveOrder` and used by
  the root and by every interior node. Move ordering is part of the contract because it decides
  how much alpha-beta prunes and therefore what the node counts mean.
- **Tie-break**: among root moves with equal score, the one that comes first in the declared move
  order wins. No other tie-break exists, and no set or dictionary is ever iterated to produce a
  move.
- **Node counting**: `nodes` counts one per child position examined by the search, including child
  positions that turn out to be terminal. The root loop itself is not a node, and a root move that
  is scored without recursion still counts as one. This definition is what makes the golden file
  in § 8 meaningful.
- **Pruning toggle**: `--pruning off` replaces every alpha-beta window with `(-∞, +∞)`, so no
  cutoff can occur. The toggle exists to make pruning measurable: same code, same ordering, same
  evaluation, with and without cutoffs. It is not a second search.
- **Transposition table**: optional and unscored. When enabled it may change `nodes`; it must not
  change the chosen move or the score at a fixed depth. An implementation that omits it is
  complete; an implementation that includes it must pass the neutrality test of § 8.
- **Fixed depth**: `--depth N`, `1 ≤ N ≤ 42`. Fully deterministic: the same position, depth and
  options produce the same move, the same score and the same node count on every run and host.
  This is the scored correctness path.
- **Budget**: `--budget-ms N`, iterative deepening from depth 1 up to `--max-depth` (default 12),
  checking the clock **between completed root depths only**, never inside a node. The last
  completed depth is reported as `depth_reached`, and its result is the answer. The clock is read
  through a delegate injected by the CLI, so `Connect4.Core` has no ambient time source.
- **Budget determinism**: the depth reached may vary with machine speed, so the budget mode is not
  required to return the same move on every run. What is required is that the answer is legal, that
  it arrives within the budget plus the tolerance of § 7, and that it equals the fixed-depth answer
  for its own `depth_reached`. A budgeted answer that no fixed-depth search of that depth would
  produce is a bug, not a timing artefact.
- **No search outside the search**: the engine has no separate "win now", "block now" or "prefer
  centre" rules. A root move may be short-circuited when it wins immediately, provided the chosen
  move is unchanged.

## 6. Evaluation contract

The evaluation is called only on non-terminal positions and only at the leaf of a search node. It
is always reported **from the perspective of the side to move**, so negamax can use it directly.

The board contains exactly **69** four-cell windows: 24 horizontal, 21 vertical, 12 on one diagonal
and 12 on the other. For a position and a side *p*, with *q* the opponent:

1. a window holding discs of both sides scores 0;
2. a window holding only *p* discs scores `w[k]` where *k* is its own disc count, with the declared
   weights `w[1] = 1`, `w[2] = 8`, `w[3] = 40`;
3. a window holding only *q* discs scores `-w[k]`;
4. each own disc in column 4 scores `+6`, each opponent disc there scores `-6`;
5. `eval = Σ windows + Σ centre`, rounded nowhere: it is an integer.

Consequences, all of which are asserted rather than promised:

- `eval` on the empty board is 0;
- `eval(pos, p) == -eval(pos, q)` for every position, because every term is antisymmetric;
- `|eval| ≤ 69 × 40 + 6 × 6 = 2796`, so `|eval(p) − eval(q)| ≤ 5592 < WIN`;
- a terminal position is never evaluated: the search scores it with § 5, so a completed four always
  produces `WIN` and never a heuristic number.

The weights are the contract, not a tuning surface: changing a weight changes the engine's answers
on the search fixtures, so a change here is a change to § 5's expected results and must be declared
in the same commit.

## 7. CLI contract

One executable, `Connect4.Cli`, with four subcommands. All output is plain text on stdout, all
diagnostics on stderr, and every number is formatted with the invariant culture.

| subcommand | purpose | scored |
|---|---|---|
| `play` | interactive game, human `X` against the engine `O` | yes, the slice |
| `scripted` | replay a move sequence, emit one JSON record for the engine's answer | yes |
| `selfplay` | engine against itself, one JSON record per ply | yes |
| `perft` | leaf counting for the perft table | yes |

### `play`

The human always moves first (`X`), the engine always moves second (`O`), and the engine answers in
budgeted mode with `--budget-ms 1000 --max-depth 12` unless overridden. The engine must answer
within that budget plus **100 ms** of scheduling tolerance, measured around the search call and not
around process start. The board is rendered exactly like this — six rows top to bottom, one space
between cells, a column header above:

```text
 1 2 3 4 5 6 7
 . . . . . . .
 . . . . . . .
 . . . . . . .
 . . . . . . .
 . . . . . . .
 . . . . . . .
move> 
```

Input is a column number `1`–`7`, `b` to reprint the board, or `q` to quit. After each engine move
the CLI prints one line with the engine's decision:

```text
engine: 4 depth=10 nodes=117615 elapsed_ms=41
```

The shape is the contract; `depth` and `nodes` depend on the implementation and `elapsed_ms` on the
host, so the tests match the line with a pattern rather than with the values. Illegal input never
crashes and never consumes a turn: `9` and `0` print `illegal: column must be 1-7`, a full column
prints `illegal: column 4 is full`, an empty line prints
`illegal: expected a column number, b or q`, and the board and the side to move are unchanged. When
the game ends the CLI prints `result: win:X`, `result: win:O` or `result: draw` and exits 0.

### `scripted`

```bash
dotnet run --project src/Connect4.Cli -c Release -- scripted --moves 4433 --depth 6
```

replays `4433` — validating legality and consistency — and prints exactly one JSON object for the
position after the sequence, for the side to move:

```json
{"ply":4,"to_move":"X","move":4,"score":-2,"depth":6,"nodes":11770,"elapsed_ms":41}
```

`--budget-ms N` may be given instead of `--depth N`, in which case the record carries
`depth_reached` in place of `depth`. `--tt on|off` and `--pruning on|off` are accepted in both
cases. Exactly one JSON object per invocation, nothing else on stdout.

A sequence that ends exactly on a terminal position is valid, and the record reports the result
instead of a move: `{"ply":7,"to_move":"O","move":null,"result":"win:X"}`, exit 0. A sequence
that continues past the terminal ply is not a position the engine reasons about, and is rejected
with exit code 2.

### `selfplay` and `perft`

`selfplay --depth N --plies M [--start <moves>]` plays the engine against itself from the given
position, prints one JSON record per ply in the shape above, then a final line
`{"plies":M,"result":"win:O"}`. `perft --depth N [--moves <prefix>]` prints
`perft(N) = <count>` followed by `elapsed_ms=<t>`.

### Exit codes

`0` success; `2` illegal move or malformed move sequence; `3` inconsistent position; `4` usage
error (unknown subcommand, `--depth` out of range, missing value). The tests assert the code, not
the message.

## 8. Test suite requirements

Three families, all under `dotnet test`, all offline, none opening a window.

**Rules (M0, M1)** — `RulesTests`, `WinDetectionTests`:

- gravity, column filling, legality of a full column, and rejection of a move after the game ended;
- win detection in all four directions, from both players, including a win formed by the last move
  and a four-disc line broken by an empty cell or by an opponent disc, which must not be a win;
- a full board with no four is a draw, and the draw is reported as `draw`, not as a win;
- cross-check: for every fixture and for 1000 gravity-legal positions generated from a fixed seed,
  incremental detection agrees with a naive scan of all 69 windows;
- every committed fixture replays legally and reaches the declared outcome at the declared ply.

**Search (M2, M3)** — `SearchTests`, `EvaluationTests`, `PruningTests`:

- the oracle: `Minimax.cs` is a plain full-window minimax with no pruning and no transposition
  table, written independently in the test project. For every search fixture and every depth 2–6,
  the engine's move and score must equal the oracle's;
- declared answers: the search fixture table (at least six positions, each a move sequence) covers
  a win in one ply, a win in two plies, a position where the only non-losing move blocks an
  immediate threat, a forced win in three plies, a quiet position, and a position that is already
  terminal. Each declares its expected `winning_moves` and its maximum plies to win, and the test
  asserts the chosen move is among them and `score ≥ WIN − max_plies`;
- from the empty board at depth 1, 2 and 4 the chosen move is column 4, by a strict score margin,
  so the answer does not depend on the tie-break;
- alpha-beta equals no-pruning: for every search fixture and every depth 2–6,
  `score(--pruning on) == score(--pruning off)` and the two moves are equal;
- pruning is measurable: from the empty board at depth 6, `nodes(--pruning on) ≤ 50% ×
  nodes(--pruning off)`, with both counts printed by the failing assertion;
- transposition-table neutrality: with `--tt on` and `--tt off`, every fixture at every depth
  2–8 returns the same move and the same score; node counts may differ and are reported;
- evaluation: the empty board scores 0; `eval(pos, X) == -eval(pos, O)` for every fixture and for
  1000 seeded positions; `|eval| ≤ 2796`; a table-driven eval test compares the engine against an
  independent window enumeration written in the test project; a position with a completed four is
  scored by the search as `WIN`, never as an evaluation value;
- determinism: `scripted` run twice on the same input produces byte-identical stdout.

**Timing and reference (M4, M5)** — `PerftTests`, `DeterminismTests`, `TimingTests`:

- the perft table of § 9 M4, exactly, from the empty board;
- perft at depth 6 from the three mid-game prefixes recorded in `tests/reference/perft.json`;
- one committed self-play game (`tests/reference/selfplay.txt`) reproduced byte for byte by
  `selfplay --depth 4 --plies 20`, twice in a row;
- the golden search file (`tests/reference/search.json`) records move, score and node count for
  every search fixture at depths 2, 4, 6 and 8 and is compared exactly: a change here is either an
  intentional engine change or a regression, and the test cannot tell the difference, which is the
  point;
- the timing workload of § 9 M5 with its declared threshold;
- isolation: a test asserts that neither `Connect4.Core` nor `Connect4.Cli` references
  `System.Net.Http`, so a network call cannot be introduced without deleting the test.

Every fixture and reference file reports its own name and field on failure, so a broken table is
readable from the failure line alone.

**Implement:** the `perft` harness, the fixture tables of § 8, and the committed reference files
`tests/reference/perft.json`, `tests/reference/search.json` and `tests/reference/selfplay.txt`.

**Acceptance:**

- perft from the empty board equals this table exactly, for every depth:

  | depth | leaves |
  |---:|---:|
  | 1 | 7 |
  | 2 | 49 |
  | 3 | 343 |
  | 4 | 2 401 |
  | 5 | 16 807 |
  | 6 | 117 649 |
  | 7 | 823 536 |
  | 8 | 5 673 234 |

  Depths 1–6 are `7^d`. Depth 7 is `7^7 − 7`, because the seven 6-ply prefixes that fill a single
  column leave six legal columns for the seventh ply. Depth 8 is `7 × (7^7 − 7 − 13 032) − 294`,
  where 13 032 is the number of 7-ply positions already won and 294 the number of 7-ply positions
  with a full column. These values follow from the rules of § 4; an implementation that disagrees
  with them is wrong, and the table is not the thing to edit.
- perft at depth 6 from the three mid-game prefixes recorded in `tests/reference/perft.json` matches
  the recorded counts;
- `selfplay --depth 4 --plies 20` reproduces `tests/reference/selfplay.txt` byte for byte, twice in
  a row, and the game it records is legal ply by ply and ends with the recorded `result`;
- `tests/reference/search.json` is compared exactly for move, score and node count at depths 2, 4, 6
  and 8 over the search fixture table;
- every committed fixture and reference file names itself and its field on failure;
- a fixture added without its reference entry fails rather than being skipped.

**Verify:**

```bash

```

### M5 — Deterministic timing benchmark (8)

**Implement:** one declared workload, one declared threshold, and the test that measures them.

```text
workload:  search --depth 10 from the empty board, no transposition table
threshold: TIMING_THRESHOLD_MS = 5000, one constant, declared once
measure:   around the search call only — no process start, no JIT warm-up, no build
report:    node count and elapsed_ms for every repetition
```

**Acceptance:**

- the workload's node count and chosen move are identical on every repetition and on every run, and
  are recorded in `tests/reference/search.json`; the measurement therefore times a fixed amount of
  work rather than a machine-dependent search;
- three repetitions each finish under `TIMING_THRESHOLD_MS`, and the reported number is the maximum
  of the three;
- the test prints node count and elapsed for each repetition, so a slow host is diagnosable from the
  failure line;
- the threshold is generous by design — a reference implementation of this Plan completes the
  workload in well under a tenth of it — because a benchmark that flakes on a busy machine produces
  noise instead of signal;
- the budgeted mode answers each of the five mid-game positions — the positions of the first five
  search fixtures — within `--budget-ms 1000` plus 100 ms, five times each, with a legal move every
  time.

**Verify:**

```bash
dotnet test -c Release --no-build --filter "milestone=M5"
```

## 10. Definition of Done

- [ ] `dotnet restore --locked-mode` and `dotnet build -c Release` succeed from a clean checkout with
      no warnings, and the engine makes no network request.
- [ ] The single start command opens a playable game: illegal input is rejected without consuming a
      turn, the engine answers within its declared budget, and a terminal position is reported as a
      declared result.
- [ ] `./verify.sh` exits 0 within 600 s and writes `verify.json` with `M0`–`M6` exactly once.
- [ ] Win and draw detection is covered in all four directions plus the edge and near-miss cases,
      and cross-checked against a naive scan.
- [ ] Negamax with alpha-beta agrees with an independent full-width minimax oracle on every fixture
      and depth.
- [ ] Pruning is demonstrated by a node-count comparison between the same search with and without
      cutoffs, not by prose.
- [ ] The evaluation weights are declared, the bound is asserted, and the perspective identity
      holds.
- [ ] The perft table of § 9 M4 matches exactly, and the committed reference files are compared
      byte for byte.
- [ ] The timing workload is fixed, its threshold is declared once, and the node count is identical
      across runs.
- [ ] No package is resolved outside the committed lockfiles, and no output depends on the host
      locale.
- [ ] `RESULT.md` records model, wall clock, turns, tokens and the harness verdict.

## 11. Operating instructions for the development agent

- Work one milestone at a time and keep the CLI playable after each one; M0 is the only milestone
  whose omission blocks everything else.
- Write the test of a milestone before its implementation. Keep `Connect4.Core` free of `Console`,
  of the ambient clock and of culture-dependent formatting: a leak there breaks determinism on a
  different host, which is exactly what this benchmark is watching for.
- Keep the win detection in one place. A second definition in the CLI or in a test is how the
  anti-diagonal case gets missed.
- Never change a declared constant — a weight, the move order, `WIN`, a perft value, the timing
  threshold — to make a test pass. If a declared constant is wrong, say so and stop; the constants
  are the specification.
- When a search answer is wrong, compare against the full-width oracle first. A disagreement with
  the oracle is an alpha-beta bug; an agreement with the oracle and a disagreement with a declared
  fixture is a fixture bug, and the two are never the same fix.
- Keep the CLI thin: parse, render, delegate. A rule in the CLI is a rule the unit tests cannot see.
- Report, before declaring a milestone done: changed files, commands run, test results, the slice
  transcript and residual risks.

## Verify

`./verify.sh` is the single verification entry point: non-interactive, timeout 600 s, exit 0 if and
only if every milestone passed. Sequence:

1. `dotnet restore --locked-mode` — the lockfiles are complete and the pins are respected. A stale
   lockfile fails here, before anything is built.
2. `dotnet build -c Release --no-restore` — warnings are errors, so a clean build is part of the
   evidence rather than a wish.
3. `dotnet test -c Release --no-build --filter "milestone=M0"` … `milestone=M5` — one run per
   milestone, so each id maps to its own exit status instead of to a single all-or-nothing result.
4. The CLI evidence, in order: the perft table of § 9 M4 through `perft --depth 1..8`; the piped
   `play` transcript of § 9 M0, asserting the board renders, the four illegal lines change nothing
   and the replies stay within budget; `scripted` on the five mid-game positions in budget mode,
   asserting legality, `depth_reached ≥ 1` and latency; `selfplay --depth 4 --plies 20` twice,
   diffed against `tests/reference/selfplay.txt` and against each other.
5. `verify.sh` maps the collected evidence onto `M0`–`M6` and writes `verify.json` in the project
   root: `schema: 1`, `benchmark: "connect4-minimax"`, every milestone id exactly once with `pass`
   and a `detail` naming the evidence, plus `notes` with the wall clock of the run.
6. `node ../../scripts/score.mjs meta.json verify.json --exit $status` is the acceptance check of
   the file itself; it is run by the operator, not by `verify.sh`.

Milestone evidence, so a `pass` is never a judgement call:

| id | passes when |
|---|---|
| `M0` | restore, build and the M0 tests passed, and the piped transcript rendered, rejected four illegal lines and answered within budget |
| `M1` | the M1 tests passed, including the naive-scan cross-check |
| `M2` | the M2 tests passed, including oracle agreement and the pruning node-count comparison |
| `M3` | the M3 tests passed, including the evaluation bound and the perspective identity |
| `M4` | the M4 tests passed, including the exact perft table and the byte-identical reference files |
| `M5` | the M5 tests passed, with the node count identical across repetitions and every repetition under the threshold |
| `M6` | steps 1–5 all ran and `verify.json` was written with the seven ids |

Determinism is asserted, not assumed: the same scripted invocation, and the same self-play game,
must produce identical bytes on two runs, with `elapsed_ms` the only field excluded from the
comparison — and even that is excluded only where it is reported, never where it decides an answer.
