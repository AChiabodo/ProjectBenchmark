# Plan — go-http-server: a concurrent service with a bounded worker pool

## 1. Goal and scope

Build an HTTP service whose *coordination* is the thing being measured. Routing and handlers are
the easy half; the half this benchmark scores is a fixed worker pool behind a bounded queue, an
admission path that decides between accepting and rejecting instead of blocking, a drain-on-shutdown
sequence with a deadline, and a test suite that runs under Go's race detector. Go is in the suite
because no other benchmark exercises a language built for concurrent services.

Nothing is downloaded and nothing is stored: one process, one loopback listener, synthetic jobs that
sleep for a declared cost, results held in memory, counters rendered as plain text. The same script
produces the same bodies, the same metric lines and the same exit code on every run and every host.

### Final functionality

- an HTTP server on the Go standard library with a declared route table and declared error codes;
- jobs submitted over HTTP, identified by a monotonic id, with a declared synthetic cost;
- a fixed set of workers consuming one bounded queue, with a declared start-up order;
- a declared backpressure policy: when the queue is full the submission is **rejected with a status
  code**, never blocked and never queued in an unbounded structure;
- results retrievable by id, held in memory under a declared bound with declared eviction;
- a middleware chain of panic recovery, request logging and a fixed-window rate limiter, applied in a
  declared order;
- a signal-triggered graceful shutdown that stops admitting work, drains the queue within a deadline
  and reports completed, failed and abandoned jobs;
- `/healthz` and a plain-text `/metrics` endpoint the tests and the scripted checks read;
- a test suite that passes `go test -race ./...`, including concurrency tests under controlled load;
- `./verify.sh` writing `verify.json` with every milestone id of `meta.json`.

### Non-goals

Any web framework, router library, middleware package or third-party module; any database, cache or
file persistence; authentication, authorisation and TLS; websockets, server-sent events and
streaming; distributed workers, message brokers, retries against a second process; metrics formats
with labels or a scraping protocol beyond plain text; profiling endpoints; structured log shipping;
deployment, hosting and CI. The job "work" is a sleep with a declared cost: the benchmark measures
coordination, so making a job expensive would measure the clock instead.

Correctness of a concurrent service is a property of its observable behaviour — status codes, bodies,
metric lines, exit codes — which is where the suite looks. It never inspects a channel, a goroutine
count or an internal type name.

## 2. Locked technical decisions

```text
Language:  Go 1.22, standard library only, one module named gohttpserver
Server:    net/http, one process, one listener, no framework, no router library
Jobs:      synthetic sleep jobs with a declared cost in milliseconds
Pool:      a fixed number of workers, one bounded queue, non-blocking reject when full
Shutdown:  signal or control route, one declared drain order, one deadline
Results:   in-memory, bounded by count, FIFO eviction of finished jobs only
Clock:     read only through one injected Now() seam, never inside a counter
Output:    JSON responses, one JSON log record per request, plain-text metrics on stdout/stderr
Tests:     go test -race ./..., loopback only, no sleep used to synchronise on an outcome
```

### Pinned dependencies and modules

| item | pin | where |
|---|---|---|
| Go toolchain | `go 1.22` in the module directive; any 1.22.x toolchain | `go.mod` |
| module requirements | none: `go.mod` has no `require` directive and stays that way | `go.mod` |
| `go.sum` | absent by construction while `require` is empty; committed with any `require` that ever appears | repository root |
| module resolution | `GOFLAGS=-mod=readonly GOPROXY=off` on every build and test | `verify.sh`, every command below |
| vet / tests | `go vet ./...`, `go test -race ./...` | `verify.sh` |

`GOPROXY=off` is what makes the offline claim checkable: with an empty `require` list and no proxy,
a build that tried to fetch a module fails instead of silently reaching the network. If a
dependency is ever added, it is pinned by a committed `go.sum`, and `GOPROXY=off` still proves the
build resolves from that file alone.

### Commands — exactly one of each

```bash
go run ./cmd/gohttp        # the single start command
./verify.sh                # the single verification command
```

`go run ./cmd/gohttp` with no flags serves on `127.0.0.1:8080` with 4 workers, a queue of 8,
`max-results` 1000, 200 requests per second and a 10 s drain deadline. Flags are optional and every
one of them has a declared default:

| flag | default | meaning | valid |
|---|---|---|---|
| `-addr` | `127.0.0.1:8080` | listen address; loopback by default | `host:port` |
| `-workers` | 4 | worker goroutines consuming the queue | ≥ 1 |
| `-queue` | 8 | queue capacity in jobs | ≥ 1 |
| `-max-results` | 1000 | bound of the result store | ≥ `workers + queue` |
| `-rate` | 200 | requests admitted per one-second window | ≥ 1 |
| `-shutdown-timeout` | 10s | drain deadline | > 0 |

A flag outside its valid range is a usage error: one line on stderr naming the flag and the violated
range, exit code 2, no listener. `go build` and `go test` are build and test steps, never a second
way to start the service.

## 3. Architecture and module boundaries

```text
go-http-server/
  go.mod                    module gohttpserver, go 1.22, no require
  cmd/
    gohttp/main.go          flag parsing, config validation, signal wiring, os.Exit
    slicecheck/main.go      the scripted slice transcript over HTTP (M0 evidence)
    loadcheck/main.go       controlled-load and backpressure checks (M2, M3 evidence)
  internal/server/
    config.go               Config, defaults, Validate
    server.go               ListenAndServe, state machine, Shutdown(ctx), drain order
    router.go               the declared route table, method dispatch, path ids
    handlers.go             submit, job, healthz, metrics, panic, shutdown
    pool.go                 workers, bounded queue, admission, execution, eviction
    jobs.go                 Job, State, id allocation, result record
    middleware.go           recover, requestlog, ratelimit, and the chain order
    ratelimit.go            fixed-window limiter over an injected Clock
    metrics.go              counters, gauges, textual rendering
    log.go                  the two JSON record shapes
    *_test.go               the suite of § 10, next to the code they drive
  verify.sh
```

The boundaries are the seams the suite uses:

- `pool.go` is the only file that touches the queue and starts or joins a worker. Everything else
  asks the pool to `Submit`, `Get` or `Drain`.
- `jobs.go` is the only place that allocates an id and the only place that mutates a job record, all
  under one mutex, so `-race` has a single authority to check.
- `metrics.go` is the only place that names a counter, and `log.go` the only place that formats a log
  record: a renamed key or a renamed counter cannot drift between the source that increments it and
  the surface that reports it.
- `Clock` is a one-method seam (`Now() time.Time`) with `time.Now` as the production value; the rate
  limiter and the drain deadline are its only readers, and the tests inject a controllable clock.
- `cmd/gohttp/main.go` is the only file that installs a signal handler or calls `os.Exit`; `server.go`
  exposes one `Shutdown(ctx) error` that both triggers call.
- Tests build a real `Server` with a real router, real pool and real store, then drive it over
  `httptest` on `127.0.0.1`; nothing in the suite fakes the pool.

## 4. HTTP contract

### Route table

| method | path | success | purpose |
|---|---|---|---|
| `POST` | `/v1/jobs` | `202` | submit one job |
| `GET` | `/v1/jobs/{id}` | `200` | one job record |
| `GET` | `/healthz` | `200` | liveness and pool gauges |
| `GET` | `/metrics` | `200` | plain-text counters and gauges |
| `GET` | `/v1/debug/panic` | — | a deliberately panicking handler, the poison route the suite drives |
| `POST` | `/v1/control/shutdown` | `202` | the second trigger of the drain of § 6 |

The last two routes are declared on purpose. `/v1/debug/panic` is how panic recovery is proved
without patching production code. `/v1/control/shutdown` exists because a POSIX signal cannot be
delivered to a process on every host Go supports; it calls the identical `Shutdown(ctx)` as the
signal handler, so the drain path has one implementation and two triggers.

Any path outside this table is `404` with `{"error":"not_found"}`. A declared path with another
method is `405` with `{"error":"method_not_allowed"}` and an `Allow` header listing the declared
methods of that path.

### Bodies

`POST /v1/jobs` accepts one JSON object:

```json
{"cost_ms": 20, "fail": false}
```

| field | type | default | rule |
|---|---|---|---|
| `cost_ms` | integer | 20 | 0–1000 inclusive; the job sleeps this long |
| `fail` | boolean | false | when true the job panics inside the worker (a declared failure path) |

`202` response, keys in this order:

```json
{"id":"job-000001","state":"queued","cost_ms":20}
```

`GET /v1/jobs/{id}` returns the current record, keys in this order:

```json
{"id":"job-000001","state":"done","cost_ms":20}
```

`state` is one of `queued`, `running`, `done`, `failed`. A record carries no timestamp and no
duration, so two runs of the same script produce byte-identical bodies. The submit response is
rendered from the admission record, so its `state` is always `queued` even if a worker has already
picked the job up.

`GET /healthz` before the drain, and during it:

```json
{"status":"ok","workers":4,"queue_depth":0}
{"status":"draining","workers":4,"queue_depth":2}
```

Errors are JSON with exactly one key, never HTML and never a Go error string:

| status | `error` | when |
|---|---|---|
| `400` | `malformed_json` | body is not one JSON object, or has trailing data |
| `400` | `bad_cost` | `cost_ms` is not an integer in 0–1000 |
| `404` | `not_found` | path outside the route table |
| `404` | `unknown_job` | id never admitted, or its record was evicted |
| `405` | `method_not_allowed` | declared path, undeclared method |
| `413` | `body_too_large` | request body above 4 KiB |
| `429` | `queue_full` | the queue had no free slot; `Retry-After: 1` |
| `429` | `rate_limited` | the rate limiter refused the request; `Retry-After: 1` |
| `500` | `internal` | a panic was recovered from |
| `503` | `draining` | the server stopped admitting work |

Rules that belong to the contract:

- every response carries `Content-Type`; JSON responses say `application/json`, `/metrics` says
  `text/plain; charset=utf-8`;
- unknown JSON fields are ignored, so a client may send extra metadata;
- a body above 4 KiB is rejected before decoding, and the remainder of the body is never read;
- `cost_ms` is validated before admission, so a rejected submission never consumes an id;
- ids are `job-%06d`, allocated on admission, monotonic within a process, never reused, and the
  counter restarts at 1 in a new process;
- response bodies are written from one struct per shape, so key order is fixed rather than incidental.

## 5. Concurrency contract

### Start-up order

1. parse and validate the config — a usage error ends the process before any listener exists;
2. build the store, the metrics and the rate limiter;
3. start the `workers` goroutines, all blocked on the queue;
4. mount the route table and the middleware chain;
5. listen and serve.

Workers are running before the first connection is accepted, so an accepted submission always finds
a live pool. There is no lazy start, no goroutine per request and no work in a request handler beyond
admission, lookup and rendering.

### Admission

One read lock on the admission `RWMutex` covers the whole decision: re-check the state, try a
non-blocking send into the queue, and on success allocate the id, insert the record and increment
`submitted`. The lock is what makes "admitted" and "closed" mutually exclusive, so § 6 can close the
queue without racing a producer.

### Queue policy — reject, never block

The queue has a fixed capacity and one consumer contract: when the non-blocking send fails, the
submission is **rejected** with `429 queue_full`, a `Retry-After: 1` header, and one increment of
`gohttp_jobs_rejected_total`. No request waits for capacity, no unbounded buffer absorbs the
overflow, and no submission is dropped silently. This is the declaration the benchmark scores:
"bounded" is measurable through a status code, not a promise in prose.

### Execution

A worker takes the next id in FIFO order, marks the record `running`, sleeps `cost_ms`, then marks it
`done`. A job submitted with `fail: true` panics inside the worker; the worker recovers its own
panic — no middleware can catch a panic in another goroutine — marks the record `failed`, increments
`gohttp_jobs_failed_total` and `gohttp_panic_recovered_total`, and takes the next job. A panicking
job never stops the pool and never stops the process.

### Results and their bound

The store keeps every unfinished record and at most `max-results` records in total; when a job
finishes and the store is full, the oldest finished record is evicted, and a lookup of an evicted id
is `404 unknown_job` exactly like an id that was never issued. Config validation enforces
`max-results ≥ workers + queue`, so an unfinished record can never be evicted and every accepted job
stays observable until it ends.

### Invariant

At every instant while the server admits work, and again once the drain has finished:

```text
submitted == completed + failed + abandoned + in_flight
```

where `in_flight` is `queue_depth` (queued) plus the jobs currently running. Together with
`submitted + rejected == submissions attempted`, this is what makes a lost job a test failure rather
than an invisible leak. A deadline that abandons work moves the remainder into `abandoned` and out of
`in_flight` in the same step, so the invariant survives the drain too.

## 6. Shutdown contract

Two triggers, one path: `SIGINT`/`SIGTERM` through `signal.Notify`, and `POST /v1/control/shutdown`
which answers `202 {"status":"draining"}`. Both call the same `Shutdown(ctx)`, whose context carries
the `-shutdown-timeout` deadline.

### Drain order — the contract

1. Flip the server state to `draining` under the admission write lock. From this instant a
   submission is `503 draining` and `/healthz` reports `{"status":"draining",…}`; reads
   (`GET /v1/jobs/{id}`) and `/metrics` keep answering, and the listener stays open.
2. Close the queue under the same lock. This cannot race a send, and after it no submission is
   admitted: every admitted id will now end `done`, `failed` or `abandoned`.
3. Wait for the workers to drain the queue and join. Queued jobs run in FIFO order, `workers` at a
   time.
4. If the deadline expires first, every job still `queued` or `running` is marked `abandoned`, its
   result is discarded, `gohttp_jobs_abandoned_total` is set to that count, the wait ends, and the
   record reports `"status":"deadline"`. A goroutine that is still sleeping is not waited for: the
   process is leaving, and the report says so.
5. `http.Server.Shutdown(ctx)` closes the listener and waits for the in-flight handlers, which by now
   are reads.
6. Write one shutdown record to stdout, then exit 0.

### Shutdown record

```json
{"event":"shutdown","status":"drained","completed":4,"failed":0,"abandoned":0,"drain_ms":21}
```

The key set is fixed and every key is always present. `status` is `drained` when `abandoned` is 0 and
`deadline` otherwise. `drain_ms` is the only clock-dependent field and is excluded from every
byte comparison.

### Exit codes

| exit | condition |
|---:|---|
| 0 | the drain finished: `drained` or `deadline`, both reported in the record and both clean |
| 1 | the listener could not be opened, or an internal invariant failed at start-up |
| 2 | usage error: an invalid flag, or a config the validator refuses |

A drain that abandons jobs because the operator configured a short deadline is a declared outcome,
not a crash: the record names the counts and the process exits 0. A process that dies on a panic, a
killed listener or a double `Shutdown` is a failure of this contract.

## 7. Middleware contract

The chain is fixed, outermost first:

```text
recover -> requestlog -> ratelimit -> router
```

- **recover** wraps everything below it. A panic becomes `500 {"error":"internal"}` when no status
  has been written yet, otherwise the response is truncated at the bytes already written and the
  connection is closed. It always increments `gohttp_panic_recovered_total`, logs the record with
  `"recovered":true`, and leaves both the process and the pool alive. A panic inside a worker is
  recovered by the worker (§ 5), because middleware runs on the request goroutine only.
- **requestlog** writes exactly one JSON record per request (§ 9), after the response so the status
  and the byte count are final.
- **ratelimit** is a fixed-window counter: at most `rate` admitted requests per one-second window,
  the window boundary read from the injected `Clock`. A request over budget is
  `429 {"error":"rate_limited"}` with `Retry-After: 1`, increments `gohttp_rate_limited_total`, and
  is *not* counted in `gohttp_requests_total`, because it never reached the router. `/healthz` and
  `/metrics` neither consume budget nor are ever rate limited: a probe must not be able to lock an
  operator out of the health of the service.
- **router** dispatches § 4 and increments `gohttp_requests_total` once per dispatched request,
  including the ones that end `404`, `405` or `500`.

Exactly one layer writes a rejection for a given request. A recording writer counts the bytes and
remembers the status, so no layer can write a second status line and no test has to guess which one
did.

## 8. Observability contract

### `/healthz`

`200` with `{"status":"ok","workers":W,"queue_depth":q}` while the server admits work, and `503` with
`{"status":"draining","workers":W,"queue_depth":q}` once the drain of § 6 has started. The endpoint
touches no lock that a submission holds for longer than a send attempt, so a probe cannot be blocked
by a busy queue.

### `/metrics`

`text/plain; charset=utf-8`, one `name value` per line, ASCII, sorted by name, no labels, no comment
lines, no timestamps. Values are integers.

| name | type | meaning |
|---|---|---|
| `gohttp_jobs_abandoned_total` | counter | jobs left queued or running when the drain deadline expired |
| `gohttp_jobs_completed_total` | counter | jobs whose execution ended `done` |
| `gohttp_jobs_failed_total` | counter | jobs whose execution panicked and was recovered |
| `gohttp_jobs_in_flight` | gauge | queued plus running jobs at scrape time |
| `gohttp_jobs_rejected_total` | counter | submissions refused with `429 queue_full` |
| `gohttp_jobs_submitted_total` | counter | submissions admitted with `202` |
| `gohttp_panic_recovered_total` | counter | recovered panics, in handlers and in workers together |
| `gohttp_queue_capacity` | gauge | the configured queue capacity |
| `gohttp_queue_depth` | gauge | jobs waiting in the queue at scrape time |
| `gohttp_rate_limited_total` | counter | requests refused with `429 rate_limited` |
| `gohttp_requests_total` | counter | requests dispatched by the router |
| `gohttp_workers` | gauge | the configured worker count |

Guarantees the suite asserts: two scrapes with no activity in between are byte-identical; counters
never decrease; the gauges are read under the same lock that mutates the state they report, so a
scrape can never show `queue_depth` larger than `queue_capacity`; every counter agrees with the
responses that produced it; and each gauge agrees with the pool state at the same moment. M0 needs
only the two job counters named in § 11; the rest of this table is M5.

## 9. Structured logging contract

One JSON object per line on stdout, diagnostics and usage on stderr, nothing else on stdout.

Request record, keys in this order, every key always present:

```json
{"event":"request","method":"POST","path":"/v1/jobs","status":202,"bytes":38,"job_id":"job-000001","recovered":false,"duration_ms":1.2}
```

`job_id` is `""` for every path that does not create or read a job. `duration_ms` is the only
clock-dependent field and is excluded from every byte comparison.

Shutdown record: § 6.

Neither record carries a timestamp, a host name, a request id or a user agent, so replaying one
script twice produces identical lines apart from `duration_ms`. The suite asserts that by running one
scripted scenario twice and diffing the captured stdout after removing `duration_ms`.

## 10. Test suite requirements

`go test -race ./...` is the gate. Tests live next to the code they drive, build a real `Server` from
a `Config` value, and reach it over `httptest` on `127.0.0.1`. Nothing is stubbed except the clock.

| family | file | what it must cover |
|---|---|---|
| routes and handlers | `router_test.go`, `handlers_test.go` | every row of the route table; every error code of § 4 with its status and body; `Allow` on `405`; body limit `413`; unknown fields ignored; ids monotonic and never consumed by a rejected submission; `cost_ms` bounds at 0 and 1000 |
| middleware | `middleware_test.go` | the chain order of § 7 observed through status and log records; a panicking handler produces `500 internal`, one `recovered` log record, one counter increment and a still-serving process; the request record key set; the limiter admits exactly `rate` requests per window under the injected clock, refuses the next one, and resets when the window advances; `/healthz` and `/metrics` are never limited |
| pool and backpressure | `pool_test.go` | N submissions on W workers with capacity C: all `done`, `in_flight` back to 0; saturating the queue yields `429 queue_full` and an equal `rejected` count; a rejected submission consumes no id and no store slot; FIFO eviction at `max-results` makes the oldest id `404 unknown_job` while an unfinished id stays `200`; `fail: true` produces `failed`, increments `failed` and `panic_recovered`, and the pool keeps serving |
| shutdown and drain | `shutdown_test.go` | with slow jobs queued, `Shutdown` completes every admitted job and reports `abandoned: 0`; with a deadline shorter than the queued work, `abandoned > 0`, `status: "deadline"`, and `Shutdown` returns within the deadline plus 500 ms; a submission during the drain is `503 draining`; a repeated `Shutdown` is a no-op; the invariant of § 5 holds after every case |
| controlled load and races | `concurrency_test.go` | 8 goroutines × 12 submissions against one live server with `workers: 2`, `queue: 4`, `cost_ms: 10`, repeated 50 times: every iteration keeps `submitted + rejected == attempts` and `submitted == completed + failed + abandoned + in_flight`, and the run leaves admission, execution, eviction and scraping all concurrent, which is what `-race` needs |
| observability | `metrics_test.go` | the twelve lines of § 8 present, sorted, integer-valued; byte-identical consecutive scrapes; counters agreeing with responses; `503`/`{"status":"draining"}` from `/healthz` during a drain |
| determinism | `determinism_test.go` | one scripted scenario run twice on fresh servers: identical bodies, identical `/metrics`, identical log lines once `duration_ms` is removed |

Rules for the suite:

- it asserts external behaviour — status codes, bodies, metric lines, log records, exit codes. No test
  asserts the channel layout, the number of goroutines, a private type name or a file's internal
  structure: a test that pins internals tests the implementation, not the service;
- no test synchronises on an outcome with `time.Sleep`; a `waitFor(t, condition, 2*time.Second)`
  helper polls with a deadline, so a slow host fails with a named condition instead of a flake;
- jobs in tests use `cost_ms` ≤ 50 and every drain deadline is at least 5× the queued work, so the
  whole suite finishes well under 60 s while still running overlapping work;
- the suite binds `127.0.0.1:0` only. A test that needed another host, another process or the network
  would be testing a different benchmark.

## 11. The vertical slice

Four jobs, two workers, a queue of four, then a clean drain. `cmd/slicecheck` performs it against a
real binary and exits 0 only when every line matches. The binary is `./bin/gohttp`, produced by
`go build -o ./bin/gohttp ./cmd/gohttp`: the same program the start command of § 2 runs.

| # | action | expected |
|---|---|---|
| 1 | start `./bin/gohttp -addr 127.0.0.1:8080 -workers 2 -queue 4 -rate 100` | the process listens; `GET /healthz` → `200 {"status":"ok","workers":2,"queue_depth":0}` |
| 2 | four × `POST /v1/jobs` with `{"cost_ms":20}` | four × `202`, ids `job-000001`…`job-000004`, `state: "queued"` in every body |
| 3 | poll `GET /v1/jobs/{id}` for the four ids until each is terminal | each body becomes exactly `{"id":"job-00000N","state":"done","cost_ms":20}` within 2 s |
| 4 | `GET /v1/jobs/job-999999` | `404 {"error":"unknown_job"}` |
| 5 | `GET /metrics` | lines `gohttp_jobs_submitted_total 4`, `gohttp_jobs_completed_total 4`, `gohttp_jobs_rejected_total 0`, `gohttp_jobs_in_flight 0` |
| 6 | `POST /v1/control/shutdown` | `202 {"status":"draining"}`, then exit code 0 within the drain deadline |
| 7 | the process's stdout | exactly one record with `"event":"shutdown"`, `"status":"drained"`, `"completed":4`, `"failed":0`, `"abandoned":0` |

The same seven steps with `SIGINT`/`SIGTERM` instead of step 6 hold wherever the host delivers a
POSIX signal; both triggers reach the same code, which is why the control route exists. The slice is
the answer to "does this model build a service that admits work, runs it through a pool, reports it,
and stops without losing or hanging a job", and it fails loudly: a pool that never rejects, a lookup
that cannot find a finished job, a drain that hangs on the deadline, or a non-zero exit each fails it
on their own.

## 12. Milestones with acceptance criteria and verification

The slice milestone carries the drain of § 6 and the bounded queue it cannot work without; M3 owns the
backpressure policy, the eviction bound and the pool's counters. Nothing is graded twice, and no

### M0 — Bootstrap, routes, worker-pool slice and drain-on-shutdown (40, slice)

**Implement:** the module (`go.mod`, no `require`); `config.go` with the flags, defaults and one
`Validate`; `cmd/gohttp/main.go` with flag parsing, exit codes and the signal wiring; the route table

`jobs.go` with the id allocator and the record; `pool.go` with `workers` goroutines, a queue of

## 14. Operating instructions for the development agent

- Work one milestone at a time and keep `go build` and `go test -race ./...` green after each; M0 is
  the only milestone whose omission blocks everything else.
- Write the test for a rule before implementing it, and change behaviour by changing this plan's
  declaration first: the plan is the specification, the code follows it.
- Keep one spelling per concept. `job`, `queue`, `worker`, `pool`, `drain`, `abandoned` are the
  vocabulary of § 5 and § 6 and are the same words in code, counters, records and tests.
- Keep one owner per fact: `metrics.go` names the counters, `log.go` formats the records, `pool.go`
  owns the queue, `jobs.go` owns the ids and the records, `server.go` owns the state machine.
- Keep the admission decision in one lock. A second lock, a second queue or an "overflow" buffer
  reintroduces the exact bug this benchmark measures.
- Grow the pool by changing `workers`, never by spawning a goroutine per request: a goroutine per
  request is a different, easier design that the slice would pass and M3 would fail.
- Prefer a smaller service that is fully declared over an extra endpoint the plan does not mention;
  health, metrics, panic and shutdown triggers are the four declared extras and nothing else is.
- Report, before declaring a milestone done: changed files, commands run, test counts, the slice
  transcript with its exit code, the metric lines observed, and residual risks.

## Verify

`./verify.sh` is the single verification entry point: non-interactive, timeout 600 s, exit 0 if and
only if every milestone passed. Sequence, all with `GOFLAGS=-mod=readonly GOPROXY=off`:

1. `go vet ./...` — static check, no network.
2. `go build -o ./bin/gohttp ./cmd/gohttp` — the single binary the scripted checks drive.
3. `go test -race ./...` — the whole suite of § 10, including the controlled-load, drain-deadline and
   determinism tests.
4. `go run ./cmd/slicecheck -binary ./bin/gohttp` — the seven steps of § 11 against the real binary,
   including the shutdown record and the exit code.
5. `go run ./cmd/loadcheck -mode queue -binary ./bin/gohttp -workers 4 -queue 4 -jobs 32` — the queue
   is driven to its limit, the `429 queue_full` responses are counted, and they are compared with
   `gohttp_jobs_rejected_total`; then the pool is drained and the shutdown record must report
   `abandoned: 0`.
6. `go run ./cmd/loadcheck -mode rate -binary ./bin/gohttp -rate 5 -requests 20` — the limiter admits
   five per window and the rest are `429 rate_limited`, with the counter agreeing.
7. The evidence is mapped onto `M0`–`M6` and written to `verify.json` in the project root next to
   `verify.sh`: `schema: 1`, `benchmark: "go-http-server"`, every milestone id exactly once with
   `pass` and a `detail` naming the evidence, plus `notes` with the wall clock of the run.

Milestone evidence, so a `pass` is never a judgement call:

| id | passes when |
|---|---|
| `M0` | the build resolves offline from an empty `require` list, and the seven steps of § 11 matched with exit 0 |
| `M1` | the router and handler tests passed, including every error code and the `Allow` header |
| `M2` | the middleware, limiter and log tests passed, and the rate-mode load check agreed with the counter |
| `M3` | the pool, backpressure and eviction tests passed, and queue mode observed `429`s equal to `gohttp_jobs_rejected_total` with `abandoned: 0` |
| `M4` | `go vet` and `go test -race ./...` both passed |
| `M5` | the health and metrics tests passed, including the twelve lines, the stable scrape and the `503 draining` status |
| `M6` | steps 1–6 all ran and `verify.json` was written with the seven ids |

Failure is reported, never hidden: a failing step records `pass: false` with the failing test or
check name for its milestone, and the remaining steps still run, so one broken feature does not erase
the evidence for the others. Every server the script starts is drained through the control route and
killed in a trap if it outlives its deadline.

## Appendix A — Toolchain (informative)

Baseline **informative, never a requirement**: adapting to the available environment is rewarded,
matching this table is not. Any Go toolchain that compiles `go 1.22` module semantics and runs the
race detector is legitimate. Go is not installed on every host by default; installing it is
environmental work and is not scored, while adapting to whatever Go is present is.

| component | baseline | note |
|---|---|---|
| Go toolchain | 1.22.x | `net/http`, `httptest`, JSON encoding and the race detector are all in the standard library |
| Module | `module gohttpserver`, `go 1.22`, no `require` | with no requirement there is no `go.sum` to commit; any future `require` commits one |
| Offline proof | `GOFLAGS=-mod=readonly GOPROXY=off` | a build that needed a fetch fails instead of reaching the network |
| Vet and tests | `go vet ./...`, `go test -race ./...` | the race detector is part of the benchmark, not an optional extra |
| Host | Windows, Linux or macOS | loopback only; the drain is reachable by signal where the host delivers one and by the control route everywhere |
| Clock | `time.Now` through one injected seam | the rate-limit window and the drain deadline are the only readers |
